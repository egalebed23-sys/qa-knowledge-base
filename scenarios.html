Сценарные кейсы

// 7 подтем · разбор инцидентов по слоям и risk-based стратегия

Зачем этот разделОстальные разделы устроены по темам: API, БД, теория. Этот — по сценариям, потому что на техническом интервью дают не тему, а ситуацию: «платёж завис», «webhook пришёл дважды», «релиз завтра». Проверяют не знание терминов, а умение пройти по слоям и обосновать решение. Механику (идемпотентность, retry, timeout, reconciliation) не дублируем — она в разделах Backend и API и Архитектура; здесь — как это собрать в ответ.
01 Каркас разбора сценария framework

Любой сценарный вопрос («пользователь жалуется, что…», «в проде видим…») разбирается одной и той же схемой. Она же спасает, когда домен незнаком — структура важнее эрудиции.

Уточнить→ Локализовать по слоям→ Гипотезы→ Проверить данными→ Оценить масштаб→ Что чиним и что предотвращает
ШагЧто говоришь вслух
1. УточнитьВоспроизводится всегда или иногда? У одного юзера или у всех? С какого момента? Что менялось — релиз, миграция, конфиг? Какое окружение и версия клиента?
2. ЛокализоватьСлой за слоем сверху вниз: браузер → сеть → API → сервис → БД/очередь → внешний провайдер. Цель — не починить, а сузить зону
3. ГипотезыДве-три конкурирующие версии, а не одна. И для каждой — чем её опровергнуть
4. ПроверитьДанными, не рассуждением: запрос в БД, поиск по логам с request-id, ответ API в DevTools
5. МасштабСколько юзеров затронуто, есть ли потеря денег/данных, есть ли workaround. Это переводит баг в приоритет
6. Фикс и профилактикаЧто чиним сейчас и какой тест/алерт не даст повториться. Senior всегда добавляет вторую часть
Главный приёмНачинай с уточняющих вопросов, даже если кажется, что ответ очевиден. Интервьюер почти всегда недоговаривает намеренно — проверяет, бросишься ли ты чинить не разобравшись. Три-четыре точных вопроса в начале дают больше, чем правильная догадка.
АнтипаттернСразу назвать причину («это точно кэш») и дальше её защищать. Сильный ответ звучит как «у меня две версии, вот чем я их различу» — и потом сужение по данным. Готовность отбросить свою гипотезу читается как опыт.
02 Локализация: Web → API → SQL/логи debugging

Формат «Web + API + SQL/логи» проверяет одно умение: по симптому в интерфейсе дойти до данных. Ключевая мысль — UI почти никогда не источник правды, он лишь отображает то, что отдал бэкенд.

СлойЧем смотрюЧто отсекаю
БраузерDevTools → Console (JS-ошибки), Network (что реально ушло и пришло)верстка и фронт-логика vs данные с сервера
ЗапросNetwork: URL, метод, заголовки, тело, статус, время ответаклиент отправил неверные данные vs сервер ответил неверно
APIтот же запрос через curl/Postman в обход UIесли через curl всё верно — проблема во фронте
Сервислоги по X-Request-ID из ответа, трейсна каком сервисе цепочки сломалось
ДанныеSQL в БД: что реально лежит в строке«не показали» vs «не сохранили»
Внешниелоги вызовов провайдера, его статус-страницанаша ошибка vs чужая недоступность
Вопрос-разделитель, который стоит задать первым«Данные неверные или неверно показаны?» Один SELECT по строке делит задачу пополам: если в БД правильно — баг выше (API-сериализация, фронт, кэш); если в БД уже неправильно — баг ниже (валидация, бизнес-логика, гонка, миграция). Этот вопрос сам по себе читается как опыт.

Сквозной идентификатор — то, что связывает слои. Без него разбор превращается в чтение логов «примерно за то же время». Как это работает: клиент или входной шлюз генерирует X-Request-ID, он идёт в каждый внутренний вызов и попадает в каждую строку лога. Дальше:

  • взял X-Request-ID из заголовков ответа (DevTools → Network → Headers)
  • нашёл по нему все логи цепочки в Kibana / OpenSearch / Grafana Loki
  • увидел, на каком сервисе появилась ошибка и с каким сообщением
  • если есть трейсинг — тот же id в Jaeger покажет тайминги по шагам
Частая находка на собесеЕсли в проекте нет сквозного request-id — это само по себе дефект наблюдаемости, и его стоит назвать. «Первое, что я бы починил — проброс request-id через все сервисы, иначе каждый инцидент разбирается вслепую» — сильная реплика.
Каверзный вопрос«Пользователь говорит: заказ оформил, а в списке заказов его нет». — Не гадать, а делить: 1) уточняю — один юзер или все, с какого времени; 2) DevTools: запрос на создание вернул 2xx? какой order_id в ответе? 3) SELECT * FROM orders WHERE id = ... — заказ в БД есть? 4) если есть — смотрю запрос списка: фильтр по статусу, по user_id, пагинация, кэш; 5) если нет — смотрю логи создания по request-id: упала транзакция, откатилась, не прошла валидация. Две ветки — «не сохранили» и «не показали» — и они чинятся в разных местах.
03 SQL и логи: что спросить у данных sql forensics

На интервью просят не абстрактный SQL, а расследование: «как проверишь, что дублей нет», «найди зависшие платежи». Набор запросов ниже закрывает большинство таких просьб.

Найти дубликаты — базовый приём через GROUP BY … HAVING COUNT(*) > 1:

-- дубли платежей по внешнему id провайдера SELECT external_payment_id, COUNT(*), SUM(amount) FROM payments GROUP BY external_payment_id HAVING COUNT(*) > 1; -- два успешных списания по одному заказу за короткий интервал SELECT order_id, COUNT(*) AS charges FROM payments WHERE status = 'captured' GROUP BY order_id HAVING COUNT(*) > 1;

Найти «зависшие» сущности — те, что застряли в промежуточном статусе дольше нормы. Главный запрос при разборе таймаутов:

SELECT id, order_id, amount, status, created_at FROM payments WHERE status = 'pending' AND created_at < NOW() - INTERVAL '15 minutes' ORDER BY created_at;

Найти рассогласование между таблицами — заказ оплачен, а платежа нет (или наоборот). Это ровно то, что ищут при разборе «деньги списались, а заказ не создался»:

-- заказы в статусе paid без успешного платежа SELECT o.id, o.status, o.created_at FROM orders o LEFT JOIN payments p ON p.order_id = o.id AND p.status = 'captured' WHERE o.status = 'paid' AND p.id IS NULL;
Приём, который стоит назватьLEFT JOIN … WHERE правая.id IS NULL — «найти то, чему нет пары». Этим одним шаблоном ищут: заказы без платежей, платежи без webhook'ов, юзеров без профиля, события в Kafka без записи в БД. На SQL-секции его спрашивают почти всегда, иногда под именем «анти-джойн».

Что искать в логах:

  • По request-id — вся цепочка одного запроса через сервисы
  • По сущности — order_id, payment_id: все события её жизненного цикла по времени
  • Всплеск ошибок — график error rate: началось внезапно (релиз, деплой провайдера) или росло плавно (утечка, заполнение диска)
  • Корреляция с деплоем — совпадает ли начало проблем с временем выката. Первый вопрос при любом инциденте
  • Retry-штормы — один и тот же вызов повторяется десятки раз: признак, что retry без backoff добивает лежащий сервис
Про чтение логов вслухНе «посмотрю логи», а что именно ищу: «беру request-id из ответа, ищу в OpenSearch по нему, смотрю первую по времени строку с уровнем ERROR — она обычно и есть причина, остальное следствие». Конкретика отличает опыт от общих слов.
04 Кейс: payment timeout payments

«Пользователь нажал «Оплатить», крутился спиннер, потом ошибка. Деньги списались. Что происходит и что проверяешь?»

Суть проблемы в одном предложенииТаймаут — это не «операция не прошла», а «мы не знаем, прошла ли она». Ответ провайдера потерялся, но сам платёж на его стороне мог выполниться. Отсюда три возможных состояния вместо двух: успех, отказ и неизвестность. Вся сложность — в третьем.

Где именно мог оборваться вызов — от этого зависит, списаны ли деньги:

Точка обрываДеньгиЧто видит юзер
Запрос не дошёл до провайдеране списаныошибка — и это правда
Дошёл, провайдер выполнил, ответ потерялсясписаныошибка — а деньги ушли
Провайдер принял в обработку, ещё не завершилрешится позжеошибка — а статус изменится через минуту

Как система должна себя вести (и что проверяет QA):

  • Idempotency-Key на запросе к провайдеру — повтор после таймаута не создаёт второй платёж, а возвращает статус первого. Без этого retry = двойное списание
  • Локальный статус до вызова. Запись pending в свою БД создаётся до обращения к провайдеру. Иначе при обрыве не останется даже следа, что попытка была
  • Дозапрос статуса (reconciliation). Фоновая задача добирает «зависшие» pending и спрашивает провайдера: «что с платежом X?». Именно она закрывает состояние «неизвестность»
  • UI не врёт. При таймауте честное «платёж обрабатывается, статус обновится» вместо «ошибка, попробуйте снова» — второе провоцирует юзера платить дважды
  • Таймаут короче, чем терпение пользователя, и с запасом меньше таймаута вышестоящего вызова — иначе клиент отвалится раньше сервера

Что конкретно проверяю:

-- 1. висящие платежи SELECT * FROM payments WHERE status = 'pending' AND created_at < NOW() - INTERVAL '15 minutes'; -- 2. не создалось ли два платежа на один заказ SELECT order_id, COUNT(*) FROM payments GROUP BY order_id HAVING COUNT(*) > 1;

Плюс логи вызова провайдера по order_id: был ли ответ вообще, какой был таймаут, сколько было ретраев. И сверка с личным кабинетом провайдера — там платёж есть?

Как воспроизвести в тестеНе ждать реального таймаута, а смоделировать: замокать провайдера через WireMock с задержкой больше таймаута; оборвать соединение прокси (Charles/mitmproxy) в момент ответа; в Testcontainers — приостановить контейнер провайдера. Проверяем: создалась ли запись pending, ушёл ли повтор с тем же Idempotency-Key, подобрала ли реконсиляция статус, что показал UI.
Каверзный вопрос«При таймауте делать retry?» — Только если запрос идемпотентный, то есть уходит с Idempotency-Key. Иначе retry на таймауте — прямой путь к двойному списанию, ведь первый запрос мог выполниться. Безопасная схема: не «повторить платёж», а «спросить статус» — сначала GET по своему идентификатору операции, и только если провайдер отвечает «такой не знаю» — повторять создание.
05 Кейс: дубль webhook async

«Провайдер прислал webhook о платеже дважды. Что произойдёт и как защититься?»

Почему дубли — норма, а не аномалияПлатёжные провайдеры работают по at-least-once: если мы не ответили 2xx за отведённое время, webhook присылается снова. Наш 200 мог потеряться по сети, обработка могла занять слишком долго — и приходит повтор. Поэтому правильная постановка не «как убрать дубли», а «как сделать обработку безопасной к повторам». Тот же принцип, что у консьюмера Kafka.

Четыре вещи, которые надо проверить — их часто путают между собой:

ПроблемаЧто должно быть
Дубль — тот же webhook дваждыдедупликация по event_id провайдера: таблица обработанных событий с уникальным индексом, повтор → 200 без побочных эффектов
Неверный порядок — refunded пришёл раньше capturedпереходы статусов проверяются по стейт-машине, «назад» не откатываем; ориентир — timestamp события, а не порядок получения
Опоздавший — webhook о старом состоянии пришёл после новогосравнение версии/времени события с текущим состоянием, устаревшее игнорируется
Подделка — webhook прислали не мы и не провайдерпроверка подписи (HMAC по телу и секрету), иначе кто угодно «подтвердит» себе оплату

Как выглядит защита в коде:

-- уникальный индекс делает дедупликацию задачей БД, а не приложения CREATE TABLE processed_events ( event_id TEXT PRIMARY KEY, processed_at TIMESTAMP DEFAULT NOW() ); -- вставка и обработка — в одной транзакции; -- повтор упадёт на PK и обработка не выполнится второй раз INSERT INTO processed_events (event_id) VALUES ('evt_123') ON CONFLICT DO NOTHING;

Ключевая деталь: запись события и сам эффект должны быть в одной транзакции. Иначе между «отметили обработанным» и «начислили» может упасть процесс — и повтор уже не сработает, а эффекта не будет.

Что ломается чаще всего· Дедупликация по своему id вместо event_id провайдера — два разных события по одному платежу (authorized и captured) схлопываются в одно, и второе теряется.
· Долгая обработка внутри webhook-хендлера — провайдер не дожидается 200, шлёт повтор, и дубли генерируем мы сами. Правильно: быстро принять, положить в очередь, ответить 200, обработать асинхронно.
· Ответ 500 на неизвестное событие — провайдер будет ретраить его вечно. Неизвестный тип лучше залогировать и вернуть 200.
Каверзный вопрос«Как протестируешь обработку дублей, если провайдер шлёт webhook сам?» — Не ждать провайдера, а слать webhook самому: curl с тем же телом и валидной подписью дважды подряд, затем с задержкой, затем параллельно в два потока (это ловит гонку, когда дедупликация сделана через SELECT-проверку вместо уникального индекса). Проверяю: баланс/статус изменился ровно один раз, во второй раз вернулся 200, в processed_events одна строка, в логах нет повторного побочного эффекта.
06 Кейс: решение о релизе release risk

«Релиз завтра, часть тестов не прошла / нашли баг / не успели регресс. Катим?» Проверяют не смелость, а умение перевести технический риск в бизнес-термины и не решать единолично.

Что оцениваю, прежде чем говорить да или нет:

ВопросЗачем
Кого затрагивает и сколько таких?1% в редком сценарии и 100% на логине — разные решения
Есть ли потеря денег или данных?необратимое — почти всегда стоп
Есть ли обходной путь?наличие workaround снижает срочность на порядок
Насколько быстро откатимся?откат за 5 минут делает риск приемлемым, откат за сутки — нет
Можно ли спрятать за флагом?тогда релиз едет, а рискованная фича выключена
Что дороже — задержка или дефект?у релиза бывает внешний дедлайн (маркетинг, договор)
Формулировка, которая работаетНе «я против релиза», а варианты с ценой каждого: «1) едем как есть — риск, что N юзеров упрутся в X, откат ~15 минут; 2) едем с выключенным флагом — фича не доедет, риск нулевой; 3) двигаем на день — успеваем регресс, но ломается анонс. Моя рекомендация — второй, потому что…». Решение принимает продакт, твоя работа — дать честную картину и рекомендацию.

Отдельный случай: «упала часть автотестов». Сначала отвечаю на вопрос «это баг продукта или баг теста?» — и это разные разговоры. Порядок: посмотреть, что именно упало (одна зона или разрозненно), есть ли у теста история flaky, воспроизводится ли руками, совпадает ли падение с изменениями в этом релизе. Красный билд без разбора — не аргумент ни за, ни против.

Два плохих ответа«Пропустим, дедлайн важнее» — скрыл риск от тех, кто принимает решение. «Категорически блокирую» — присвоил себе полномочия бизнеса. Оба читаются как незрелость. Senior выносит решение туда, где есть контекст и полномочия, со своей аргументированной позицией.

После релиза сценарий не заканчивается — назови это отдельно: smoke на проде сразу после выката, наблюдение за error rate и latency против baseline в первые полчаса, заранее оговорённые критерии отката («если 5xx выше X% — катимся назад»). Это переводит ответ из «протестировали и отпустили» в «управляем риском до и после».

07 Практика: risk-based стратегия practical

Практическая секция обычно звучит как «вот наш продукт, набросай стратегию тестирования». Ждут не список видов тестирования, а приоритизацию: что тестируем в первую очередь и почему именно это.

Шаблон ответа — пять шагов:

ШагЧто делаю
1. Уточняю контекстКто пользователи и сколько их? Есть ли деньги и персональные данные? Регуляторика? Как часто релизимся? Какая команда и что уже автоматизировано?
2. Режу на областиРазбиваю продукт на домены: auth, платежи, основной бизнес-флоу, интеграции, отчётность
3. Оцениваю риск каждойвероятность сбоя × ущерб. Вероятность: новый код, сложность, частота изменений, история багов. Ущерб: деньги, данные, число затронутых, репутация, штрафы
4. Раздаю покрытие по рискуHigh — автотесты на всех уровнях + мониторинг; Medium — базовые автотесты; Low — чек-лист и exploratory. Явно говорю, что не тестируем
5. Называю метрикиКак пойму, что стратегия работает: escape rate, время прогона, доля упавших релизов
Матрица рисков — как проговоритьРисуй словами таблицу «вероятность × ущерб»: высокий ущерб + высокая вероятность — сюда идёт основное покрытие и мониторинг; высокий ущерб + низкая вероятность (редкая, но дорогая операция вроде массового возврата) — обязательно покрыть, пусть даже вручную по чек-листу; низкий ущерб + высокая вероятность — автотесты, если дёшево; низкий + низкий — осознанно не тестируем. Последняя клетка — самая важная в ответе: умение назвать, что мы сознательно не покрываем, отличает стратегию от списка пожеланий.

Пример на типовом кейсе — веб-магазин с оплатой:

Что добавить в конце, чтобы ответ звучал завершённымТри вещи, о которых забывают: тестовые данные (откуда берём, как чистим, как изолируем параллельные прогоны), окружения (где живут провайдеры — sandbox или моки) и прод (smoke после деплоя, алерты, кто дежурит). Стратегия, которая заканчивается на «прогнали тесты», выглядит неполной.
Каверзный вопрос«У вас неделя и продукт, который вы видите впервые. С чего начнёте?» — 1) Полчаса на разговор с продактом и разработчиком: что приносит деньги, что ломалось в прошлом, чего боятся сами. 2) Смотрю прод: где ошибки в мониторинге, о чём пишут в саппорт — это готовая карта рисков, добытая бесплатно. 3) Покрываю revenue-critical путь end-to-end, остальное — чек-лист и exploratory. 4) Ставлю smoke в пайплайн, чтобы не катить разломанное. История багов и жалобы пользователей — лучший источник приоритетов, чем собственные догадки о продукте.

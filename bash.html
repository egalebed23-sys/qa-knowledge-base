01 Bash: команды и навигация cli basics

Большинство серверов и CI-раннеров работают на Linux, а общение с ними идёт через shell (часто Bash). QA заходит в консоль, чтобы посмотреть логи, проверить сервис, запустить тесты или подготовить окружение.

Что закрыть перед скринингомBash: файлы и права, пайпы, редиректы, процессы, сеть, кавычки, переменные, exit codes и cleanup. Docker: image/container, Dockerfile, Compose, порты, volumes, сети, healthcheck и дебаг. Kubernetes: Pod, Deployment, Service, probes, namespace/context, requests/limits, rollout и разбор проблемных состояний.

Базовая навигация:

pwd # где я сейчас (путь) ls -la # список файлов, включая скрытые и права cd /var/log # перейти в директорию cat app.log # вывести содержимое файла cp source target # скопировать mv old new # переместить или переименовать rm file # удалить файл mkdir tests # создать директорию
АналогияShell — это REPL операционной системы: вводишь команду, получаешь результат, как в интерактивном Python. Файловая система — дерево: / корень, ветки — директории, листья — файлы. cd — переход по дереву, ls — посмотреть, что в текущем узле.

Пути: / — корень (абсолютный путь), ~ — домашняя директория, . — текущая, .. — родительская.

Права доступа (ls -l показывает rwxr-xr-x):

  • r (read=4), w (write=2), x (execute=1) — для владельца, группы, остальных
  • chmod 755 file — владельцу всё (7=rwx), остальным чтение+выполнение (5=r-x)
  • chmod +x script.sh — сделать файл исполняемым
  • chown user file — сменить владельца

find — поиск файлов:

find . -name "*.log" # все .log в текущем дереве find /var -mtime -1 # изменённые за последний день

Пайпы и редиректы — основа мощи shell: соединяешь простые команды в цепочки.

command > file.txt # вывод в файл (перезапись) command >> file.txt # дописать в конец command 2> errors.txt # перенаправить ошибки (stderr) command 2>&1 # stderr туда же, куда сейчас направлен stdout command < input.txt # взять stdin из файла command | tee out.txt # показать вывод и одновременно записать его cmd1 | cmd2 # вывод cmd1 на вход cmd2 (пайп) cmd1 && cmd2 # cmd2 только при успехе cmd1 cmd1 || cmd2 # cmd2 только при ошибке cmd1 cmd1 ; cmd2 # выполнить обе независимо от результата
АналогияПайп | — это композиция функций: cmd2(cmd1(input)). Выход одной команды становится входом следующей. grep error app.log | wc -l = «отфильтруй ошибки → посчитай».
Каверзный вопрос«Что значит 2>&1?» — Перенаправить stderr (поток ошибок, дескриптор 2) туда же, куда идёт stdout (вывод, дескриптор 1). Нужно, чтобы поймать и обычный вывод, и ошибки в один файл/пайп: ./script.sh > all.log 2>&1.
Безопасная работа в консолиCLI не прощает ошибок — особенно на чужих/боевых машинах:
  • Перед rm — проверь, где ты: pwd и ls, что именно удаляешь
  • rm -rf — осознанно: один неверный путь сносит дерево без корзины и без отмены
  • cp -i, mv -i — режим с подтверждением перезаписи (safer)
  • Не запускать curl ... | bash из интернета, не прочитав, что внутри — это выполнение чужого кода
  • На production — сначала read-only диагностика (смотреть логи/статус), а не команды, меняющие состояние
02 Логи и текст главное для QA

Главное, зачем QA в консоли — разбирать логи. Когда тест упал или сервис ведёт себя странно, ответ обычно в логах. Базовый инструментарий:

grep "error" app.log # найти строки со словом error tail -f app.log # следить за логом в реальном времени tail -n 100 app.log # последние 100 строк head app.log # первые строки less app.log # листать большой файл
Аналогияgrep — это filter() по строкам файла: оставляет только те, что подходят под условие. tail -f — как подписка на поток событий: новые строки появляются на экране по мере записи, как live-лента.

grep с флагами — рабочая лошадка:

ФлагЧто делает
-iигнорировать регистр (Error = error)
-rрекурсивно по всем файлам в директории
-vинвертировать — строки БЕЗ совпадения
-nпоказать номера строк
-cпосчитать количество совпадений
-A 3 / -B 3 / -C 33 строки после / до / вокруг совпадения

Пайпы для фильтрации логов — комбинируешь команды:

# посчитать, сколько ошибок в логе grep -c "ERROR" app.log # следить за логом, но только за строками с ошибками tail -f app.log | grep -i error # найти ошибки и показать 5 строк контекста вокруг grep -C 5 "Exception" app.log

Обработка текста: wc -l (посчитать строки), sort (сортировать), uniq -c (уникальные + счётчик).

# топ-10 самых частых ошибок в логе grep "ERROR" app.log | sort | uniq -c | sort -rn | head

awk и sed — для более сложной обработки (знать базово):

  • awk '{print $1}' — вывести первый столбец каждой строки
  • sed 's/old/new/g' — заменить текст
jq — работа с JSON (важнее awk/sed для QA)API отдаёт JSON, structured-логи в JSON — jq вытаскивает поля без регулярок:
# достать поле из ответа API curl -s api/orders/1 | jq '.status' # отфильтровать массив: только неуспешные curl -s api/orders | jq '.[] | select(.status != "paid")' # из structured-логов вытащить request_id ошибок cat app.log | jq 'select(.level=="error") | .request_id'
Полезнее, чем углублять awk/sed: большинство данных у QA — это JSON (API, логи).

Реальный кейс — найти ошибку по request-id (связка с дебагом 500 из раздела API):

# 1. из ответа API взял X-Request-ID: abc-123 # 2. ищем все логи этого запроса через все сервисы grep -r "abc-123" /var/log/services/ # 3. нашли строку с трейсом — видно, где упало

Централизованное логирование — на реальном проде grep по файлам почти не используют. Логи всех сервисов стекаются в одну систему с поиском через UI (сервисов десятки, логи в контейнерах исчезают при перезапуске). Основные системы — одной таблицей:

СистемаКратко
ELK / KibanaElasticsearch + Kibana-UI. Классика, часто self-hosted
Grafana Lokiлоги рядом с метриками в Grafana, популярен с Kubernetes
Datadogоблачный all-in-one (логи + метрики + трейсы + APM), платный
Splunkэнтерпрайз, мощный язык запросов, дорогой

Принцип у всех один — тот же, что у grep, но через UI и по всем сервисам сразу: поиск по тексту, фильтр по полям (service:payment AND level:error), time range, дашборды/алерты, корреляция по request-id.

Structured loggingСовременные сервисы пишут логи не строками, а JSON: {"level":"error","service":"payment","request_id":"abc-123","msg":"..."}. Это позволяет фильтровать по полям (level:error), а не парсить текст регулярками. Для QA — намного удобнее искать: точечные фильтры вместо grep по сырому тексту.
В реальном миреQA-автоматизатор использует оба подхода. Kibana / Datadog / Grafana — для дебага в проде и на staging: найти ошибку по request-id, посмотреть всплеск 500-х, собрать путь запроса через микросервисы. grep / tail на сервере — когда централизованного сбора нет: CI-раннер, локальный контейнер, быстрый дебаг. Принцип одинаковый (поиск → фильтр → контекст), меняется только инструмент. Знать стоит и то, и другое.
Делегируй LLMГенерация команд: «Напиши команду: найти в app.log все строки с ERROR за сегодня, сгруппировать по тексту ошибки и показать топ-5 по частоте.»

Разбор awk/sed: вставь непонятную команду → «Объясни, что делает эта awk-команда построчно.»
03 Процессы, порты, сеть diagnostics

Вторая частая задача — проверить, жив ли сервис и что с ним. Процессы:

pgrep -af python # найти процессы python с аргументами ps aux # снимок всех процессов top # или htop — что потребляет CPU/память в реальном времени kill 1234 # обычное завершение (SIGTERM) — сначала пробуем это kill -9 1234 # принудительное (SIGKILL) — только если не завершается
АналогияПроцесс — это запущенный экземпляр программы, как объект — экземпляр класса. У каждого свой PID (как id объекта). kill — отправить сигнал процессу; kill -9 — жёсткое завершение, как принудительно завершить зависший поток.

Порты — какой процесс на каком порту слушает (частая проверка «занят ли порт», «поднялся ли сервис»):

lsof -i :5432 # кто слушает порт 5432 ss -tlnp # все слушающие TCP-порты + процессы # (netstat — старый аналог ss)

Сеть и диагностика:

КомандаЗачем
curl urlвыполнить запрос к API из консоли, посмотреть ответ
curl -vс деталями: заголовки, статус, TLS
ping hostотвечает ли хост на ICMP; запрет ICMP ещё не означает, что сервис недоступен
dig / nslookupрезолвится ли домен в IP (DNS)
nc -zv host 443открыт ли порт на хосте
# проверить API прямо из консоли curl -X POST https://api.shop.com/orders \ -H "Authorization: Bearer token" \ -H "Content-Type: application/json" \ -d '{"product_id": 42}'

curl --fail-with-body удобен в CI: сохраняет тело ошибки, но возвращает non-zero для HTTP 4xx/5xx. Токены лучше брать из защищённой переменной окружения и не печатать через set -x или логи пайплайна.

Если приложение запущено как Linux-сервис:

systemctl status my-service # состояние systemd-сервиса journalctl -u my-service -n 100 # последние 100 записей журнала journalctl -u my-service -f # следить за новыми записями

SSH — подключиться к удалённому серверу (смотреть логи, проверить сервис):

ssh user@server.com # подключиться (по ключу, не паролю) scp file.txt user@server:/tmp # скопировать файл на сервер
В реальном миреДля QA-автоматизатора этот набор — must-have: curl (проверить API), grep/tail (логи), lsof/ss (порты), ssh (на сервер). Это не «системное администрирование», а ежедневный дебаг. Глубокое системное администрирование (настройка демонов, iptables, тюнинг ядра) знать не нужно — это зона DevOps/SRE.
Каверзный вопрос«Сервис не отвечает. Как по шагам диагностируешь в консоли?» — 1) процесс жив? pgrep -af service или systemctl status, 2) слушает порт? ss -tlnp | grep :8080, 3) отвечает локально? curl localhost:8080/health, 4) что в логах? journalctl или tail, 5) резолвится DNS и доступен ли порт? dig, nc. Идёшь от процесса к локальному порту, затем к сети и логам.
04 Bash-скрипты scripting

Скрипт — набор команд в файле, чтобы не вводить их каждый раз. Для QA — автоматизация рутины: поднять окружение, прогнать тесты, собрать логи.

#!/usr/bin/env bash # shebang — найти Bash через PATH echo "Running tests..." pytest tests/ echo "Done"

Запуск: chmod +x run.sh (сделать исполняемым) → ./run.sh.

Bash или shsh script.sh явно запускает системный sh и может проигнорировать Bash-shebang. Конструкции [[ ... ]], массивы и pipefail не гарантированы в POSIX sh. Если скрипт написан для Bash, запускай ./script.sh или bash script.sh.

Переменные, условия, циклы:

#!/usr/bin/env bash NAME="staging" # переменная (без пробелов вокруг =) echo "Env: $NAME" # использование через $ export NAME # передать переменную дочерним процессам if [[ "$NAME" == "prod" ]]; then echo "Production environment selected" fi for file in *.log; do # цикл по файлам echo "Processing $file" done

Кавычки — частый вопрос и источник реальных ошибок. Одинарные кавычки сохраняют текст буквально: 'Hello $NAME'. Двойные выполняют подстановку: "Hello $NAME". Раскрытие переменной почти всегда пиши как "$value", иначе пробелы и символы * ? [ могут разбить один аргумент на несколько или запустить globbing.

Спецпеременные: $0 — имя скрипта, $1, $2 — аргументы, $# — их число, $? — код последней команды, $$ — PID shell. Для передачи всех аргументов используй "$@": каждый исходный аргумент сохранится отдельно, включая значения с пробелами.

Функции и подстановка команды:

run_tests() { local report_dir="$1" pytest tests/ --junitxml="$report_dir/results.xml" } current_branch=$(git branch --show-current) run_tests "${REPORT_DIR:-reports}"

Реальный кейс QA — скрипт поднимает окружение, ждёт сервис, гоняет тесты:

#!/usr/bin/env bash set -euo pipefail cleanup() { docker compose down } trap cleanup EXIT # cleanup выполнится и при ошибке docker compose up -d # поднять зависимости # polling с дедлайном вместо фиксированного sleep timeout 30 bash -c 'until nc -z localhost 5432; do sleep 1; done' if pytest tests/ --maxfail=1; then result=0 else result=$? fi exit "$result"
Полезные привычкиset -u ловит необъявленные переменные, pipefail — ошибку в любой части пайпа, trap ... EXIT гарантирует cleanup. set -e полезен, но у него есть исключения в условиях, циклах и пайпах, поэтому его нельзя считать полной обработкой ошибок. Ожидание сервиса делай через polling с дедлайном, а не sleep 30 наугад.
Exit codes — почему CI «видит» падениеКаждая команда возвращает код: 0 = успех, не 0 = ошибка. CI считает шаг проваленным, если команда вернула non-zero — поэтому pytest с упавшими тестами возвращает не 0, и пайплайн краснеет. Проверить код последней команды: echo $?. В примере код тестов сохраняется в result и возвращается через exit "$result", а trap успевает остановить окружение.

ShellCheck — статический анализатор shell-скриптов. Он ловит некавыченные переменные, недостижимый код, ошибки редиректов и проблемы совместимости: shellcheck run-tests.sh. Хороший ответ на вопрос «как ревьюить Bash кроме запуска».

Делегируй LLMBash-синтаксис легко забывается — отличная задача для LLM:

«Напиши bash-скрипт: поднять docker compose, дождаться готовности Postgres на 5432, прогнать pytest, в конце остановить compose и вернуть код тестов.»
05 Docker containers

Docker запускает приложение с его файлами и зависимостями в изолированном контейнере. Для QA это воспроизводимое окружение: можно поднять нужную версию БД или сервиса одной командой и повторить тот же запуск в CI.

docker ps # запущенные контейнеры docker ps -a # все, включая остановленные docker logs container_id # логи контейнера docker run --rm -e POSTGRES_PASSWORD=test postgres:16 # удалить контейнер после остановки docker stop <container> # остановить контейнер docker rm <container> # удалить остановленный контейнер
Image и containerОбраз — неизменяемый шаблон со слоями файловой системы и конфигурацией запуска. Контейнер — экземпляр образа с собственным процессом и изменяемым слоем. Один образ может породить много контейнеров; удаление контейнера не удаляет образ.
Контейнер против VMВиртуальная машина содержит гостевую ОС и собственное ядро. Контейнер — изолированный процесс, который разделяет ядро хоста, поэтому обычно стартует быстрее и требует меньше ресурсов. Это не «маленькая VM»: изоляция и модель безопасности отличаются.

Запуск с параметрами:

# поднять Postgres для тестов docker run -d \ -p 5432:5432 \ -e POSTGRES_PASSWORD=test \ --name test-db \ postgres:16

-d запускает в фоне, -p host:container публикует порт, -e передаёт переменную, --name задаёт читаемое имя.

docker compose (V2 — единая команда, не старый docker-compose) — поднять несколько сервисов вместе (app + БД + Redis) одним файлом:

docker compose up -d --build # пересобрать и поднять сервисы docker compose ps # состояние контейнеров docker compose logs -f app # следить за логами сервиса app docker compose down # остановить и удалить контейнеры/сеть docker compose down -v # дополнительно удалить volumes: данные пропадут

Dockerfile — рецепт сборки образа. Собирается командой docker build -t myimage:1.0 . (точка — контекст сборки):

FROM python:3.12 WORKDIR /app COPY requirements.txt . # сначала ТОЛЬКО зависимости RUN pip install -r requirements.txt COPY . . # код — последним CMD ["pytest"]

Слои и кэш сборки — частый вопрос по Dockerfile. Инструкции формируют кэшируемые результаты, а изменения файловой системы сохраняются слоями. При пересборке Docker переиспользует подходящий кэш; изменение раннего шага обычно инвалидирует зависящие от него следующие шаги.

Почему requirements копируют отдельноЕсли написать COPY . . до pip install, то любая правка кода инвалидирует слой и зависимости будут ставиться заново — каждая сборка по несколько минут. Копируя сначала только requirements.txt, ты добиваешься, что слой с pip install пересобирается лишь при изменении списка зависимостей. Правило: от редко меняющегося к часто меняющемуся.

Инструкции, которые путают:

ПараРазница
CMD vs ENTRYPOINTCMD задаёт команду или аргументы по умолчанию и переопределяется аргументами docker run. ENTRYPOINT обычно фиксирует исполняемый файл, а аргументы из run дописываются; явно заменить его можно через --entrypoint. Частый приём: ENTRYPOINT ["pytest"] + CMD ["tests/"]
COPY vs ADDCOPY просто копирует. ADD умеет ещё качать по URL и авто-распаковывать архивы — из-за этой «магии» рекомендуют всегда COPY, кроме случая, когда распаковка нужна осознанно
RUN vs CMDRUN выполняется при сборке образа, CMD — при запуске контейнера
EXPOSE vs -pEXPOSE 8080 документирует ожидаемый порт образа, но не открывает его на хосте. -p 8080:80 при запуске действительно публикует порт контейнера

.dockerignore — что не класть в контекст сборки (.git, venv, __pycache__, локальные артефакты). Без него контекст раздувается, сборка тормозит, а в образ могут утечь лишние файлы и секреты.

Volumes — где живут данные. Контейнер эфемерен: удалил — данные внутри исчезли. Чтобы сохранить, монтируют том:

docker run -v mydata:/var/lib/postgresql/data postgres:16 # named volume — управляет Docker docker run -v $(pwd)/tests:/app/tests myimage # bind mount — папка с хоста
  • Named volume — Docker хранит сам, переживает пересоздание контейнера. Для данных БД
  • Bind mount — конкретная папка хоста внутрь контейнера. Удобно подсунуть тесты или конфиг без пересборки образа

Сети — почему из контейнера не видно localhost. Классическая ловушка: внутри контейнера localhost — это сам контейнер, а не твоя машина и не соседний контейнер.

Как обращаться правильно· Контейнер → контейнер в одном compose: по имени сервиса — postgres:5432, а не localhost:5432. Compose поднимает общую сеть и заводит DNS по именам сервисов.
· Контейнер → хост-машина: host.docker.internal (Docker Desktop на Windows/macOS).
· Хост → контейнер: только через проброшенный порт -p 5432:5432. Без -p порт снаружи недоступен, даже если сервис внутри слушает.
· Сервис внутри должен слушать 0.0.0.0, а не 127.0.0.1 — иначе он принимает только соединения изнутри контейнера.

Дебаг контейнера — частая задача, когда «в контейнере не работает»:

docker exec -it container sh # shell внутри; bash может не быть в slim-образе docker logs -f --tail 100 cont # смотреть логи в реальном времени docker inspect container # детали: сеть, env, volumes, health docker stats container # CPU и память в реальном времени

Зайдя внутрь через exec, проверяешь изнутри: переменные окружения (env), доступность других сервисов (curl, nc), файлы конфигов.

Testcontainers — библиотека, которая поднимает реальные зависимости (Postgres, Kafka) в Docker прямо из автотеста и останавливает их после теста. Тест работает с настоящей БД, а не моком. Это связка с разделом CI/CD (раздел 07).

Multi-stage build — собрать в одном образе, а в финальный положить только результат. Так из образа исчезают компиляторы, dev-зависимости и исходники: меньше размер и меньше поверхность атаки.

FROM python:3.12 AS builder # стадия сборки COPY requirements.txt . RUN pip install --user -r requirements.txt FROM python:3.12-slim # финальный образ — только нужное COPY --from=builder /root/.local /root/.local COPY . . CMD ["pytest"]

Короткий depends_on не ждёт готовности — он гарантирует запуск зависимости раньше потребителя, но Postgres «стартовал» ещё не означает «принимает подключения». Для ожидания readiness нужен healthcheck и длинная форма с condition: service_healthy:

services: db: image: postgres:16 healthcheck: test: ["CMD-SHELL", "pg_isready -U postgres"] interval: 5s retries: 10 tests: depends_on: db: condition: service_healthy # ждать ЗДОРОВЬЯ, а не старта

Альтернатива без compose — wait-for-it.sh / retry в самом тесте. Testcontainers делает это за тебя из коробки.

Registry и теги. Образы хранятся в реестре (Docker Hub, GitHub Container Registry, приватный Nexus/Harbor): docker pull / docker push. Про теги важно понимать: latest — не «последняя версия», а просто тег по умолчанию, который можно перезаписать. Поэтому «у меня и в CI разное поведение на одном latest» — обычная история. Для воспроизводимости фиксируют версию (postgres:16.2) или digest (postgres@sha256:...).

Безопасность образаНе копируй в образ .env, приватные ключи и токены: слои и история сборки могут их сохранить. Для секретов сборки используй BuildKit secrets, для runtime — механизм секретов платформы. Бери минимальный доверенный base image, запускай процесс не от root через USER, сканируй образ и обновляй закреплённые версии осознанно.

Жизненный цикл и restart policy. Контейнер живёт, пока жив его главный процесс (PID 1). docker inspect показывает exit code: 0 — штатное завершение, 1 — общая ошибка приложения, 137 — процесс получил SIGKILL (часто OOM, но причину надо подтвердить через OOMKilled и события), 143 — SIGTERM. Политика --restart задаёт перезапуск; при always падающий контейнер может перезапускаться по кругу.

Каверзный вопрос«Контейнер сразу падает после запуска. Как дебажить?» — 1) docker logs container, 2) docker inspect container — exit code, OOM, env, mounts и health, 3) проверить команду/entrypoint и наличие файлов, 4) при необходимости запустить образ с переопределённым entrypoint: docker run --rm -it --entrypoint sh image. Контейнер останавливается, когда завершается его главный процесс.
06 Kubernetes orchestration

Kubernetes (k8s) — оркестратор контейнеров. Когда контейнеров десятки и сотни, кто-то должен их запускать, перезапускать упавшие, масштабировать, распределять по серверам. Это и делает k8s.

АналогияDocker запускает один контейнер на одной машине. Kubernetes — как оркестратор/супервизор для целого парка: следит, чтобы нужное число копий всегда работало, перезапускает упавшие, распределяет нагрузку. Как process manager (типа supervisord), но для контейнеров на кластере машин.

Архитектура в одном абзаце. Control plane хранит желаемое состояние и принимает решения: API server принимает команды, scheduler выбирает node, controllers сводят фактическое состояние к желаемому, etcd хранит состояние кластера. На worker nodes kubelet следит за Pod, а container runtime запускает контейнеры.

Декларативная модель. В YAML-манифесте обычно есть apiVersion, kind, metadata и spec: мы описываем желаемое состояние и применяем его через kubectl apply -f file.yaml. Поле status заполняет кластер фактическим состоянием. Поэтому при отладке важно сравнивать spec и status, а не только читать файл из Git.

Ключевые понятия:

  • Pod — минимальный развёртываемый объект: один или несколько тесно связанных контейнеров с общей сетью и подключёнными volumes
  • Deployment — управляет репликами подов: «держи 3 копии сервиса всегда живыми»
  • Service — стабильная сеть и DNS для набора Pod: Pod пересоздаются и меняют IP, адрес Service остаётся
  • Namespace — логическое разделение (dev / staging / prod в одном кластере)
  • Ingress — маршрутизация внешнего HTTP-трафика внутрь кластера (какой домен/путь → какой Service)
  • ConfigMap — конфиг (env-переменные, файлы настроек) отдельно от образа
  • Secret — то же для чувствительного (пароли, токены). Хранится в base64, то есть кодирование, а не шифрование — без включённого шифрования etcd это не защита
  • Labels и selectors — метки связывают объекты: например, Service направляет трафик только в Pod, которые совпали с его selector

Какой workload выбрать:

ОбъектКогда нужен
Deploymentstateless-сервис, реплики, rolling update и rollback
StatefulSetстабильные имена, порядок запуска и отдельное хранилище для каждой реплики
DaemonSetпо Pod на каждой подходящей node: лог-агент, мониторинг
Job / CronJobодноразовая задача / запуск задачи по расписанию

Типы Service: ClusterIP доступен внутри кластера и используется по умолчанию; NodePort публикует порт на nodes; LoadBalancer запрашивает внешний балансировщик у облачной платформы. Ingress — не тип Service, а HTTP/HTTPS-маршрутизация поверх Service.

Probes — как кластер понимает, жив ли под. Спрашивают почти всегда, и путают чаще всего:

ProbeВопросЧто будет при провале
livenessконтейнер ещё способен продолжать работу?после порога ошибок контейнер перезапускается
readinessготов принимать трафик?Pod исключается из endpoints Service, но не перезапускается
startupдолгий старт закончился?до успеха отключает liveness/readiness; после порога ошибок контейнер перезапускается
Чем это оборачивается для QA· Слишком строгая liveness — под перезапускается под нагрузкой, потому что не успел ответить на проверку. Снаружи выглядит как «сервис случайно рвёт соединения».
· Нет readiness — трафик идёт в под, который ещё не прогрелся: после каждого деплоя короткая пачка 502/503. Классический баг, который ловится smoke-тестом сразу после выката.
· Readiness ходит в БД — упала БД, все поды разом стали not ready, сервис пропал из балансировщика целиком.
Сначала проверь контекстkubectl действует в текущем кластере и namespace. Перед изменяющими командами проверь kubectl config current-context и явно указывай -n staging. Одинаковые имена ресурсов в dev, staging и prod — обычная история.

Основные команды диагностики:

kubectl get deploy,svc,pods -n staging # состояние объектов kubectl get pods -n staging -o wide # node, IP и дополнительные детали kubectl describe pod pod-name -n staging # conditions и события kubectl logs pod-name -n staging --tail=100 # последние логи kubectl logs pod-name -n staging --previous # логи прошлого запуска контейнера kubectl exec -it pod-name -n staging -- sh # shell; bash может отсутствовать kubectl get pods -n staging -w # следить за изменениями kubectl port-forward -n staging svc/api 8080:80 # локальный доступ к Service

Если в Pod несколько контейнеров, для logs и exec укажи -c container-name. По label можно собрать логи всех реплик: kubectl logs -n staging -l app=api --all-containers --prefix.

port-forward особенно полезен — пробрасываешь порт сервиса из кластера на свою машину и тестируешь его локально через curl/Postman.

Requests и limits — почему Pod «сам умирает». requests — объём ресурсов, который scheduler учитывает при размещении, limits — верхняя граница. Превышение лимита памяти может завершить контейнер с причиной OOMKilled (часто exit code 137). При превышении CPU-limit контейнер не убивают, а замедляют через throttling. Если тесты падают по таймауту только в кластере, проверь usage, requests и limits.

Типовые состояния и причины — по ним сразу видно класс проблемы:

Состояние / причинаЧто означает
CrashLoopBackOffконтейнер стартует и падает по кругу — ошибка приложения, конфига или проваленная liveness
ImagePullBackOffне может скачать образ — опечатка в теге, нет доступа к приватному реестру
Pendingнекуда поставить — не хватает ресурсов на нодах или не привязался volume
OOMKilledвышел за limit по памяти, убит ядром

Хранилище. Обычный Pod эфемерен. PV описывает ресурс хранения, PVC — запрос workload на хранилище, StorageClass задаёт способ динамического создания volume. При Pending проверяй не только CPU/RAM, но и события PVC.

Масштабирование. Deployment можно масштабировать вручную через kubectl scale. HPA меняет число реплик по метрикам, например CPU или latency. QA проверяет границы: scale-up под нагрузкой, scale-down после неё, отсутствие потери запросов и достаточные requests, без которых CPU-based HPA может работать некорректно.

Helm пакетирует связанные Kubernetes-манифесты в chart и подставляет параметры из values.yaml. Для QA полезно уметь прочитать values окружения, сравнить фактический image tag/config и выполнить helm template или helm lint до установки.

Выкатка и откат: kubectl rollout status deploy/name — дождаться завершения, kubectl rollout history deploy/name — посмотреть ревизии, kubectl rollout undo deploy/name — откатить. При rolling update какое-то время работают обе версии, поэтому QA проверяет backward compatibility API/БД, readiness новых Pod, отсутствие 5xx и правильный image tag.

В реальном миреНа большинстве QA-позиций важнее уверенная диагностика, чем администрирование кластера. Но в infrastructure, security и platform-продуктах от SDET могут ждать чтения YAML/Helm, развёртывания тестовых сред и проверки autoscaling. Глубина зависит от продукта, базовые связи объектов и алгоритм диагностики нужны в любом случае.
Каверзный вопрос«Pod в CrashLoopBackOff. Что делать?» — 1) проверить context и namespace, 2) kubectl get pod -o wide и describe — conditions/events, 3) logs --previous -c ... — логи завершившегося контейнера, 4) проверить command/args, image tag, ConfigMap/Secret, probes и limits. CrashLoopBackOff — это увеличивающаяся пауза между повторными запусками; первопричина находится в завершении контейнера и событиях.

01 Pytest: основы basics

pytest — самый популярный фреймворк для тестов на Python. Тест — это обычная функция с assert:

# test_math.py def test_addition(): assert 2 + 2 == 4 def test_string(): assert "hello".upper() == "HELLO"

Запуск — команда pytest в терминале, тесты он находит сам по соглашениям об именах (ниже).

Главное преимуществоОбычный assert вместо assertEqual/assertTrue из unittest. При падении pytest сам показывает, что было слева и справа: assert 2 + 2 == 5 → видно 4 != 5. Работает это за счёт assertion rewriting: при импорте pytest переписывает assert в тестовых модулях и conftest.py, чтобы при падении вывести значения. В обычных модулях-хелперах этого нет — assert там упадёт голым AssertionError без деталей. Лечится pytest.register_assert_rewrite("helpers") в conftest или тем, что хелпер возвращает значение, а проверяет его сам тест.

Соглашения об именах (по ним pytest находит тесты): файлы test_*.py или *_test.py, функции test_*, классы Test* без __init__ с методами test_*. Шаблоны меняются в конфиге: python_files, python_classes, python_functions.

Полезные флаги запуска:

КомандаЧто делает
pytest -vподробный вывод (имя каждого теста)
pytest -k "login"запустить тесты, в имени которых есть login
pytest -xостановиться на первом падении
pytest --maxfail=2остановиться после 2 падений
pytest test_api.py::test_loginконкретный тест
pytest -sпоказывать print (не перехватывать вывод)
pytest --lf / --ffтолько упавшие в прошлый раз / сначала упавшие, потом остальные
pytest --durations=1010 самых медленных тестов — с этого начинают ускорение
pytest --coтолько собрать список тестов, не запуская: проверить, что выбирают -k и -m
pytest --fixturesвсе доступные фикстуры и где они объявлены

Структура теста — AAA (Arrange-Act-Assert):

def test_user_creation(): data = {"name": "Иван"} # Arrange user = create_user(data) # Act assert user.name == "Иван" # Assert

Статусы в отчёте — частый вопрос «чем ERROR отличается от FAILED»:

  • FAILED — упал сам тест: не прошёл assert или исключение в теле теста
  • ERROR — упала подготовка или уборка: исключение в фикстуре до или после теста. Сам тест мог и не запуститься, поэтому ERROR — сигнал смотреть на окружение и данные, а не на проверяемую логику
  • SKIPPED, XFAIL (ожидаемо упал), XPASS (ожидали падение, а прошёл) — см. раздел 06

Проверка исключений:

import pytest def test_divide_by_zero(): with pytest.raises(ZeroDivisionError): result = 1 / 0 def test_age_validation(): with pytest.raises(ValueError, match=r"must be \d+") as exc: validate_age(10) assert exc.value.args[0].startswith("age") # сам объект исключения

match — это регулярное выражение, и ищется оно через re.search, то есть в любом месте сообщения. Точки, скобки и другие спецсимволы в ожидаемом тексте надо экранировать или обернуть в re.escape(). Через as exc доступны тип, сообщение и атрибуты исключения. Для сравнения float — pytest.approx (почему — раздел Python, «Синтаксис»).

Фреймворки, которые стоит уметь сравнить:

ИнструментПодход и применение
pytestлаконичные функции, обычный assert, фикстуры, параметризация и плагины; основной универсальный выбор для Python AQA
unittestстандартная библиотека и xUnit-стиль: классы, setUp/tearDown, методы assertEqual; меньше внешних зависимостей, больше шаблонного кода
Robot Frameworkkeyword-driven acceptance-тесты с табличным синтаксисом; читаем для не-разработчиков, но сложнее поддерживать при большой программной логике
BehaveBDD-сценарии на Gherkin и Python step definitions; полезен, когда команда действительно совместно работает со спецификациями в формате Given/When/Then

Интеграционные тесты с pytest проверяют совместную работу реальных компонентов: например, API записывает заказ в БД, а тест читает его обратно. Фикстуры поднимают клиент, соединение и тестовые данные, а через yield гарантируют очистку. Такие тесты маркируют отдельно, запускают в воспроизводимом окружении и не подменяют моками те границы, взаимодействие с которыми проверяют.

@pytest.mark.integration def test_order_is_saved(api_client, db): order = api_client.create_order() stored = db.get_order(order.id) assert stored.status == "created"
Каверзный вопрос«Чем pytest лучше unittest?» — Голый assert с понятным выводом вместо методов assertEqual; фикстуры гибче setUp/tearDown (scope, переиспользование, зависимости); параметризация одним декоратором; богатая экосистема плагинов. unittest хорош тем, что в стандартной библиотеке — не нужно ставить.
02 Фикстуры главная тема

Фикстура (fixture) — подготовка того, что нужно тесту: данные, соединение с БД, авторизованный клиент. Объявляешь через @pytest.fixture, тест получает её как аргумент.

import pytest @pytest.fixture def user(): return {"name": "Иван", "role": "admin"} def test_user_is_admin(user): # fixture передаётся по имени assert user["role"] == "admin"
АналогияФикстура — это dependency injection для тестов: тест объявляет, что ему нужно (аргумент user), pytest сам создаёт и подставляет. Тест не занимается подготовкой — он просто получает готовое, как функция получает аргументы.

Setup/teardown через yield — код до yield это подготовка, после — очистка:

@pytest.fixture def db_connection(): conn = connect_to_db() # setup yield conn # отдаём тесту conn.close() # teardown (всегда выполнится)

Scope — как часто пересоздавать фикстуру:

ScopeСоздаётся
function (по умолчанию)на каждый тест заново
classодин раз на класс тестов
moduleодин раз на файл
sessionодин раз на весь прогон (дорогие ресурсы: БД, токен)

Есть ещё package — один раз на пакет тестов. Два правила, которые спрашивают:

  • Фикстура может зависеть только от фикстур того же или более широкого scope. Session-фикстура, которая просит function-фикстуру, падает с ScopeMismatch, и тест получает статус ERROR: долгоживущий объект не может держать ссылку на то, что пересоздаётся на каждый тест
  • Уборка идёт в обратном порядке. Если order зависит от user, сначала создаётся user, потом order, а убираются они наоборот — сначала order, потом user. Поэтому заказ удаляется раньше, чем пользователь, и внешние ключи не мешают

conftest.py — файл с общими фикстурами и хуками, его не импортируют: pytest находит его сам. Таких файлов может быть несколько, по одному на уровень папок. Фикстуры из conftest видны тестам этой папки и всех вложенных, а ближайший conftest переопределяет фикстуру с тем же именем — так в tests/admin/ подменяют общий client на админский, не трогая остальные тесты. Корневой conftest держит общее: клиент API, авторизацию, подключение к БД.

# conftest.py @pytest.fixture(scope="session") def api_client(): client = APIClient(base_url="...") client.login("user", "pass") return client # один авторизованный клиент на весь прогон

Фикстуры зависят от фикстур — выстраиваются в цепочку:

@pytest.fixture def order(api_client, user): # использует две другие фикстуры return api_client.create_order(user_id=user.id)

Фабрики — фикстура возвращает функцию, чтобы создавать объекты с разными параметрами:

@pytest.fixture def make_user(): def _make(role="user"): return create_user(role=role) return _make # в тесте: make_user(role="admin")

Встроенные фикстуры — даёт сам pytest, мини-примеры:

def test_file(tmp_path): # tmp_path — pathlib.Path, временная папка f = tmp_path / "data.txt" f.write_text("hello") def test_output(capsys): # перехват stdout / stderr print("done") assert capsys.readouterr().out == "done\n" def test_logs(caplog): # перехват логов для проверки do_something() assert "ошибка" in caplog.text

Используй tmp_path (на pathlib.Path), а не устаревший tmpdir. monkeypatch — подмена переменных окружения и атрибутов — разобран в разделе 04.

Объект request — встроенная фикстура, через которую фикстура узнаёт, для кого её вызвали:

  • request.param — текущее значение из params или indirect-параметризации
  • request.node.name — имя теста: удобно для уникальных тестовых данных и имён скриншотов
  • request.addfinalizer(fn) — уборка без yield; сработает, даже если фикстура упала уже после регистрации
  • request.config.getoption("--env") — своя опция командной строки (раздел 05, хуки)

Параметры у самой фикстуры — @pytest.fixture(params=[...]): каждый тест, который её берёт, прогоняется по разу на значение. В отличие от indirect (раздел 03), значения задаёт фикстура, а не тест.

@pytest.fixture(params=["admin", "user"]) def role(request): return request.param def test_profile(role): ... # test_profile[admin], test_profile[user] @pytest.mark.usefixtures("clean_db") # значение не нужно — нужен только побочный эффект def test_report(): ...
autouse-фикстуры@pytest.fixture(autouse=True) применяется ко всем тестам в области без явного указания в аргументах. Удобно для сквозной подготовки (сброс состояния, общий лог). Опасно — создаёт «неявную магию»: тест зависит от того, чего не видно в его сигнатуре. Применяй для действительно сквозного и очевидного, иначе тесты становится трудно читать и дебажить.
Главное про teardownУборка после yield выполнится, даже если тест упал, — на этом держится изоляция: создал данные в БД, удалил после, независимо от результата. Но если упала сама подготовка до yield, уборка этой фикстуры не запустится, а тест получит ERROR. Опасно, когда фикстура создаёт несколько ресурсов подряд: первый создан, на втором упало, и первый остаётся мусором. Защита — один ресурс на одну фикстуру, а цепочку строить зависимостями; либо регистрировать уборку через request.addfinalizer сразу после создания каждого ресурса.
Каверзный вопрос«Фикстура со scope=session создаёт юзера, тесты его меняют. В чём риск?» — Тесты перестают быть изолированными: один тест поменял состояние общего юзера → следующий падает или зависит от порядка. Дорогие ресурсы (соединение, токен) шарить можно, а изменяемые данные лучше создавать на каждый тест (function scope) или откатывать в teardown.
03 Параметризация parametrize

Параметризация — один тест прогоняется на множестве входных данных. Не дублируешь код, не пишешь 10 почти одинаковых тестов:

@pytest.mark.parametrize("value, expected", [ (2, 4), (3, 9), (5, 25), ]) def test_square(value, expected): assert value ** 2 == expected # pytest создаст 3 отдельных теста
АналогияПараметризация — как цикл по тест-кейсам, но каждая итерация — отдельный тест в отчёте. Упал один набор данных — видно, какой именно, остальные прошли. Это лучше, чем цикл внутри одного теста (там первое падение прячет остальные).

ids — читаемые имена для каждого набора (видны в отчёте):

@pytest.mark.parametrize("email, valid", [ ("user@mail.com", True), ("no-at-sign", False), ("", False), ], ids=["valid", "no_at", "empty"]) def test_email_validation(email, valid): assert is_valid_email(email) == valid

В отчёте будет test_email_validation[valid], [no_at], [empty] — сразу понятно, какой случай упал.

pytest.param — современный способ задать id и пометить отдельный набор (например, известный баг через xfail):

@pytest.mark.parametrize("value, expected", [ pytest.param(2, 4, id="positive"), pytest.param(0, 0, id="zero"), pytest.param(-1, 1, id="negative", marks=pytest.mark.xfail), ]) def test_square(value, expected): ...

Это прямое применение техник тест-дизайна (раздел теории): классы эквивалентности и граничные значения превращаются в наборы параметров.

Параметризованные фикстуры (indirect) — один тест прогоняется на разных конфигурациях (роли, окружения, клиенты). Особенно полезно для API-тестов:

@pytest.fixture def client(request): role = request.param # значение приходит из parametrize return make_client(role=role) @pytest.mark.parametrize("client", ["admin", "user"], indirect=True) def test_access(client): # тест прогонится для admin и user ...

indirect=True направляет параметр в фикстуру, а не в тест напрямую — фикстура успевает подготовить ресурс под каждый набор.

Несколько parametrize на одном тесте перемножаются. Два декоратора по 2 и 3 значения дают 6 тестов, ещё один на 4 значения — уже 24. Удобно для матрицы «роль × браузер», но легко раздуть набор незаметно. Если нужны конкретные сочетания, а не все, их перечисляют кортежами в одном parametrize.

@pytest.mark.parametrize("role", ["admin", "user"]) @pytest.mark.parametrize("browser", ["chromium", "firefox", "webkit"]) def test_login(role, browser): ... # 2 × 3 = 6 тестов

Тест-данные — где брать:

  • Inline — прямо в parametrize (простые случаи)
  • Фабрики — factory_boy для объектов с реалистичными полями
  • Faker — фейковые данные (имена, email, адреса)
  • Внешние файлы — JSON/CSV/YAML для больших датасетов
Уникальность данныхПри параллельном запуске тесты не должны конфликтовать за одни данные. Генерируй уникальное: f"user_{uuid4()}@test.com", а не хардкод "test@test.com" — иначе два теста создадут юзера с одним email и один упадёт.
04 Моки в pytest mocking

Мок подменяет внешнюю зависимость (API, БД, время) на управляемую заглушку, чтобы тест не зависел от внешнего мира. Базовые инструменты — monkeypatch (встроенный) и mocker (плагин pytest-mock).

def test_with_monkeypatch(monkeypatch): # подменить переменную окружения monkeypatch.setenv("API_URL", "http://test") # подменить функцию monkeypatch.setattr(time, "time", lambda: 12345)
ЗачемТест должен проверять твою логику, а не работу чужого сервиса. Если код ходит в платёжку — мокаешь её ответ, и тест не зависит от того, доступна ли платёжка сейчас. Это делает тесты быстрыми и стабильными (см. также раздел API → контрактное тестирование).

pytest-mock — это плагин (не часть ядра pytest), даёт фикстуру mocker — обёртку над unittest.mock, удобнее в pytest:

def test_order_payment(mocker): # подменяем функцию, задаём что вернёт mock_pay = mocker.patch("app.payment.charge") mock_pay.return_value = {"status": "success"} result = create_order(amount=100) assert result.paid is True mock_pay.assert_called_once() # проверка вызова mock_pay.assert_called_with(amount=100)

Мок HTTP-вызовов — через библиотеку responses (как в разделе API):

@responses.activate def test_external_api(): responses.add(responses.GET, "https://api.ext.com/data", json={"key": "value"}, status=200) result = fetch_data() assert result["key"] == "value"
Patch там, где используетсяКлассическая ошибка: мокать функцию там, где она определена, а не там, где используется. Если app.service делает from app.payment import charge, то патчить надо app.service.charge, а не app.payment.charge. Иначе мок не сработает, тест ходит в реальный код.

Что задаёт поведение мока:

  • return_value — что вернуть при каждом вызове
  • side_effect — исключение (проверить обработку ошибки), список значений (вызов за вызовом — так тестируют retry: сначала таймаут, потом успех) или функция
  • Mock vs MagicMock — второй дополнительно поддерживает «магические» методы: len(), итерацию, with. mocker.patch по умолчанию создаёт MagicMock
  • autospec — мок повторяет сигнатуру настоящего объекта. Без него Mock молча примет опечатку в имени метода и вызов с неверными аргументами, и тест останется зелёным, когда настоящий код уже упадёт
from unittest.mock import Mock, create_autospec pay = Mock(side_effect=[TimeoutError, {"status": "ok"}]) # 1-й вызов — исключение, 2-й — успех m = Mock() m.chrage(100) # опечатка — Mock проглотит молча m = create_autospec(PaymentClient, instance=True) m.chrage(100) # AttributeError — такого метода нет m.charge(1, 2, 3) # TypeError — неверная сигнатура # в pytest-mock: mocker.patch("app.service.charge", autospec=True)

Что мокать, а что нет (связка с разделом API):

  • Мокать: чужие внешние сервисы (платёжки, сторонние API), медленное (сеть), недетерминированное (время, random)
  • Не мокать: своё ядро (бизнес-логику, которую и тестируешь), свою БД (лучше реальная через Testcontainers)
Каверзный вопрос«Замокал всё, тесты зелёные — это хорошо?» — Не обязательно. Over-mocking опасен: тест проверяет моки, а не систему. Если замокал собственную бизнес-логику — тест зелёный, а реальный код сломан. Правило: мокай границы (внешнее, дорогое), а ядро тестируй по-настоящему. Зелёный тест на моках ≠ работающий код.
05 Организация фреймворка архитектура тестов

«Расскажи про свой автотест-фреймворк» — типовая структура E2E-проекта:

project/ ├── tests/ # сами тесты, разбиты по доменам/фичам │ ├── conftest.py # общие фикстуры (корневые) │ ├── api/ │ │ └── test_orders.py │ └── ui/ │ └── test_checkout.py ├── clients/ # обёртки над API (Client Object) │ └── order_client.py ├── pages/ # Page Object для UI │ └── checkout_page.py ├── data/ # фабрики и тест-данные │ └── factories.py ├── config/ # настройки окружений (dev/stage/prod) │ └── settings.py ├── utils/ # хелперы: логирование, ожидания, форматтеры ├── conftest.py # корневой conftest ├── pytest.ini # конфиг pytest, маркеры ├── pyproject.toml # зависимости, ruff/mypy ├── .env.example # шаблон переменных (без секретов!) └── README.md # как запустить
Главный принципТест отвечает на вопрос «что проверяем», всё остальное вынесено: как ходить (clients/pages), с какими данными (data), куда (config). Тест не должен содержать ни голых HTTP-запросов, ни селекторов, ни хардкода URL — он читается как бизнес-сценарий. Если разговор уйдёт в SOLID, здесь работают ровно два принципа: SRP — страница и клиент отдельно от проверок, и DIP — зависимости приходят фикстурой, а не создаются внутри теста (разбор всех пяти — в разделе Python, «ООП»).

Слои (отделяют тесты от деталей): Client/Page-слой (как взаимодействуем) → Test-слой (что проверяем) → Data-слой (с чем). Зависимости идут в одну сторону: тест использует клиент и данные, но клиент не знает про тесты.

Маркеры — помечать и группировать:

@pytest.mark.smoke def test_critical_path(): ... # pytest -m smoke / pytest -m "not slow"

Config и секреты: окружения через переменные (.env локально, secrets в CI), .env в .gitignore, в репо только .env.example. Секреты — никогда в код (связка с разделом Безопасность).

Хуки — точки расширения pytest, объявляются в conftest.py. Два самых частых на практике:

# conftest.py def pytest_addoption(parser): # своя опция: pytest --env dev parser.addoption("--env", default="stage") @pytest.fixture(scope="session") def base_url(request): return URLS[request.config.getoption("--env")] @pytest.hookimpl(wrapper=True) def pytest_runtest_makereport(item, call): # результат каждой фазы теста report = yield setattr(item, f"rep_{report.when}", report) # rep_setup / rep_call / rep_teardown return report @pytest.fixture def page(browser, request): page = browser.new_page() yield page if request.node.rep_call.failed: # скриншот только упавших allure.attach(page.screenshot(), name=request.node.name, attachment_type=allure.attachment_type.PNG) page.close()

Это и есть ответ на частый вопрос «как сделать скриншот при падении UI-теста»: хук сохраняет отчёт о фазе на объекте теста, фикстура в уборке смотрит, упал ли тест. Ещё один полезный хук — pytest_collection_modifyitems: менять список собранных тестов, например автоматически вешать маркер api на всё из папки tests/api/.

Паттерны проектирования автотестов — частый senior-вопрос «какие паттерны используешь и зачем»:

ПаттернСуть и зачем
Page Object (POM)страница = класс с локаторами и методами. Тесты не знают про селекторы; поменялась вёрстка — правишь в одном месте. Для UI
Client / Service Objectто же для API: класс-обёртка над эндпоинтами домена. Тесты работают с client.create_order(), не с HTTP. Аналог POM для бэкенда
Factory / Builderсоздание тест-данных: фабрика генерит объект с дефолтами + уникальными полями, builder собирает сложный объект по частям. Убирает копипасту setup
Fixture / DIвстроен в pytest: подготовка и очистка ресурсов, внедрение зависимостей в тест через аргументы. Замена setup/teardown
Singletonодин экземпляр на прогон (конфиг, сессия). Осторожно с общим состоянием при параллели

Реже: Screenplay и Fluent interface — достаточно знать названия.

Каркас ответа «расскажи про свой фреймворк»Структурируй так: 1) стек — pytest + requests, Allure для отчётов; 2) слои — клиенты по доменам (Client Object), тесты не знают про HTTP; 3) фикстуры — авторизация и тест-данные в conftest, очистка через teardown; 4) данные — фабрики, уникальные значения, подготовка через API, а не через UI; 5) маркеры — smoke/regression для разделения прогонов; 6) CI — параллельный запуск, Allure-отчёт, gate на merge. Заверши тем, что улучшил: «сократил флак с X до Y», «ускорил прогон вдвое».
В реальном миреХороший фреймворк оценивают не по «красоте», а по тому, легко ли в нём писать новые тесты и читать чужие. Если для нового теста надо скопировать 20 строк настройки — слои плохие. Если тест читается как бизнес-сценарий (order = client.create(); assert order.status == "paid") — фреймворк удался.
Каверзный вопрос«Зачем client-слой, если можно просто requests в тесте?» — При росте до сотен тестов голые requests превращаются в ад поддержки: поменялся эндпоинт — правишь в 50 местах. Client-слой = единая точка: меняешь в одном месте. Плюс тесты читаются как сценарии, а не как HTTP-запросы. Это та же причина, по которой для UI делают Page Object.
06 Запуск, отчёты, CI execution

Тесты должны гоняться автоматически в CI на каждый PR (см. раздел CI/CD) и давать понятный отчёт. Базовые инструменты:

  • pytest-xdist — параллельный запуск
  • pytest-cov — покрытие кода
  • Allure — красивые отчёты с шагами и аттачами

Где конфигурируется pytest — частый вопрос. В pytest.ini или pyproject.toml (современнее, всё в одном файле):

# pyproject.toml [tool.pytest.ini_options] testpaths = ["tests"] # где искать тесты python_files = "test_*.py" # шаблон файлов с тестами addopts = "-v --strict-markers" # опции по умолчанию markers = [ "smoke: быстрые критичные тесты", "slow: долгие тесты", ]

--strict-markers — заставляет регистрировать все маркеры (защита от опечаток в @pytest.mark).

Параллельный запуск — главный способ ускорить:

pytest -n 4 # в 4 процесса (pytest-xdist) pytest -n auto # по числу ядер

Требование — изоляция тестов: не зависят друг от друга и от общих данных, иначе при параллели начнут конфликтовать.

xdist: session-фикстура — одна на воркер, а не на прогонПри -n 3 session-фикстура выполнится три раза — по разу в каждом процессе-воркере. Три логина ещё терпимо, но если она сидит базу или создаёт общего пользователя, воркеры начнут мешать друг другу. Варианты: сделать подготовку идемпотентной или своей для каждого воркера (фикстура worker_id даёт gw0, gw1…, без xdist — master); одноразовую подготовку закрыть файловой блокировкой (filelock, пример есть в документации xdist); или вынести её из pytest в отдельный шаг CI до запуска тестов. Тесты, которым нужно идти вместе на одном воркере, группируют: --dist loadscope (по модулю или классу) или --dist loadgroup с маркером @pytest.mark.xdist_group("name").

Разделение прогонов маркерами (связка с CI/CD):

pytest -m smoke # быстрые на каждый PR pytest -m regression # полный набор ночью

Flaky-тесты — pytest-rerunfailures позволяет перезапускать упавшие (--reruns 2), но это костыль, не лечение: прячет проблему, а не решает (см. CI/CD).

skip / xfail — управление «непроходящими» тестами:

@pytest.mark.skip(reason="фича в разработке") def test_new(): ... @pytest.mark.skipif(sys.platform == "win32", reason="только Linux") def test_linux_only(): ... @pytest.mark.xfail(reason="известный баг JIRA-123") def test_known_bug(): ... # ожидаем падение
xfail — не способ прятать плохой тестxfail = «знаем, что падает, есть заведённый баг» — тест помечен честно. Важная деталь: если такой тест вдруг прошёл (XPASS), по умолчанию прогон не падает — XPASS только появляется в сводке (-rX), и маркер может годами висеть на давно починенном баге. Чтобы XPASS ронял прогон, нужен @pytest.mark.xfail(strict=True) или xfail_strict = true в конфиге — тогда починили баг, тест покраснел, маркер пришлось снять. И xfail ставят только с реальной причиной или тикетом — это не то же, что закомментировать или skip-нуть сломанный тест, чтобы не мешал.

Коды выхода pytest — по ним CI решает, красный ли шаг:

  • 0 — всё прошло; 1 — есть упавшие тесты
  • 2 — прогон прерван, в том числе ошибкой при сборе тестов (опечатка в импорте); 3 — внутренняя ошибка pytest; 4 — неверное использование командной строки
  • 5 — не собрано ни одного теста. Ловушка CI: pytest -m smoke, когда маркер не стоит ни на одном тесте, даёт код 5 и красный пайплайн. Обратная ошибка — обернуть запуск в || true и потерять настоящие падения

Ещё три плагина, которые спрашивают:

  • pytest-randomly — каждый раз запускает тесты в случайном порядке и печатает seed в шапке. Ловит зависимость от порядка, которую последовательный запуск прячет. Воспроизвести падение — --randomly-seed=<seed>, отключить — -p no:randomly
  • pytest-timeout — --timeout=60 убивает зависший тест, вместо того чтобы держать CI-джобу до общего таймаута
  • Allure — @allure.step("Создать заказ") на методах клиента превращает вызовы в шаги отчёта, allure.attach(...) прикладывает запрос, ответ или скриншот (пример — хук в разделе 05)

Ускорить медленный suite на стороне pytest: параллелизация (-n auto), переиспользование дорогих фикстур (session scope), убрать sleep → явные ожидания. Процессная часть (разделить на pre-merge/nightly, сдвиг по пирамиде, value автотестов) — в разделе CI/CD.

Каверзный вопрос«Тест иногда падает, иногда проходит. Что делаешь?» — Не --reruns и забыть. Ищу причину flaky: гонки/тайминги (sleep вместо ожидания), зависимость от порядка тестов, общие тест-данные при параллели, нестабильный внешний сервис (мокать), недетерминизм (время, random). retry — временная мера, пока чиню корень.
AI в работе с pytest — сводка по всему разделуВопрос «как используешь AI» задают один раз, а не по каждой теме. Что реально экономит время:

Где помогает: превратить правила валидации в parametrize-наборы по классам эквивалентности и границам, сразу с ids через pytest.param; набросать каркас тестов к функции — позитив, негатив, граничные, исключения; разложить тест с голыми requests по слоям — клиент, фабрики данных, фикстуры, маркеры.

Что всегда проверяешь руками: изоляцию — общее состояние и зависимость от порядка LLM пропускает чаще всего, а именно тут рождается flaky; цель patch — модель охотно патчит место определения, а не использования; моки без autospec, которые принимают что угодно; доменные кейсы и приоритеты — их модель не знает.

Готовый ответ на собесе: «Параметризованные наборы и черновики тестов генерирую, дальше читаю как чужой код: смотрю, изолированы ли тесты, туда ли стоит patch, не проглатывают ли моки неверные вызовы. Доменные проверки пишу сам».

01 Модель и базовый цикл basics

Git — распределённая система контроля версий. Обычный clone содержит локальную историю и позволяет создавать commits, branches и просматривать изменения без постоянного соединения с сервером.

working tree --git add--> index --git commit--> local repository local repository --git push--> remote repository
  • Working tree — файлы, которые сейчас редактируются; они могут быть untracked или modified
  • Index / staging area — точный набор изменений для следующего commit
  • Local repository — сохранённый граф commits и refs внутри .git
  • Remote repository — отдельная копия; origin лишь обычное имя remote, не специальное слово Git
git clone <url> # получить repository и working tree git status --short # состояние файлов git diff # working tree vs index git add -p # выбрать отдельные hunks git diff --staged # index vs HEAD: что попадёт в commit git commit -m "fix login timeout" # локальный снимок git push # обновить remote ref
Зачем нужен indexОн позволяет собрать атомарный commit из части текущих правок. Если в одном файле одновременно исправлен баг и начат рефакторинг, git add -p помогает зафиксировать их отдельно.

git commit -am "message" автоматически добавляет modified/deleted tracked files, но не включает новые untracked-файлы.

Три варианта diff, которые важно не путать:

КомандаСравнение
git diffнезастейдженные изменения: working tree ↔ index
git diff --stagedподготовленный commit: index ↔ HEAD
git diff HEADвсе локальные правки: working tree ↔ HEAD
git show <commit>metadata и patch конкретного commit

Commit содержит ссылку на tree проекта, parent commit или несколько parents у merge, автора/коммитера, время и сообщение. Его object ID зависит от содержимого. Логически Git показывает snapshots; физически packfiles могут хранить объекты с delta compression.

HEAD обычно символически указывает на текущую branch, а через неё — на commit. В detached HEAD он указывает прямо на commit. Branch и tag — тоже refs: branch двигается с новыми commits, tag обычно фиксирует конкретную версию.

Fetch, pull и push:

  • git fetch --prune скачивает новые objects/refs и обновляет remote-tracking refs вроде origin/main, не меняя текущую local branch и working tree
  • git pull сначала делает fetch, затем интегрирует upstream по опциям или config: fast-forward only, rebase, merge либо squash. Поэтому нельзя считать, что pull всегда равен fetch + merge
  • git push -u origin feature-x публикует branch и задаёт upstream; после этого pull/push могут работать без явных имён
.gitignoreОн не даёт Git начать отслеживать подходящие untracked-файлы. Уже tracked-файл правило не исключит: его сначала убирают из index через git rm --cached. Секреты, локальные окружения, кэши и генерируемые отчёты лучше исключать до первого commit.
Каверзный вопрос«Чем fetch отличается от pull?» — Fetch только обновляет моё локальное представление remote. Pull после fetch ещё меняет текущую branch выбранным способом интеграции. Когда важно сначала увидеть расхождение, делаю fetch, затем смотрю log/diff и явно выбираю merge, rebase или fast-forward.
02 Ветки, remote и tags branches

Branch — двигающаяся ссылка на commit, а не копия каталога. Новый commit сдвигает текущую branch вперёд; создание branch почти ничего не стоит.

git fetch origin git switch -c feature-login origin/main # branch от свежего origin/main # ... изменения, add, commit ... git push -u origin feature-login # publish + upstream
ИмяЧто это
mainlocal branch; двигается локальными commits/merge/rebase/reset
originимя remote и набор настроек его URL/refspec
origin/mainlocal remote-tracking ref: состояние remote branch по последнему fetch
upstreamсвязь local branch с remote-tracking branch для pull, push и статуса ahead/behind
Важное различиеУдаление local branch не удаляет remote branch и наоборот. git branch -d feature-x удаляет локальную ссылку, git push origin --delete feature-x — удалённую. git fetch --prune убирает устаревшие remote-tracking refs.

Detached HEAD — HEAD указывает прямо на commit, например после git switch --detach <sha>. Просматривать и тестировать старую версию безопасно. Если здесь созданы нужные commits, до их очистки создают ссылку: git switch -c rescue-branch.

Tags фиксируют версии. Lightweight tag — простая ссылка. Annotated tag хранит автора, дату, сообщение и может быть подписан; он подходит для release:

git tag -a v2.4.0 -m "release 2.4.0" git push origin v2.4.0 # отправить tag явно git show v2.4.0

Release tag не передвигают молча: опубликованное имя версии должно продолжать указывать на тот же object. Исправление выпускают новым tag.

Несколько задач одновременноgit worktree add ../hotfix -b hotfix origin/main создаёт второе working tree того же repository. Можно держать feature и hotfix в разных каталогах без stash и постоянного switch; одна branch обычно не может быть checkout одновременно в двух worktrees.
Каверзный вопрос«Чем switch отличается от checkout?» — checkout исторически и переключает branches/commits, и восстанавливает paths. switch отвечает за переход между branches/commits, restore — за содержимое working tree/index. Более узкие команды яснее показывают намерение, но restore file всё равно может уничтожить незакоммиченные правки.
03 Merge, rebase и squash главная тема

Merge, rebase и squash решают похожую задачу — перенести изменения, но по-разному меняют commit graph.

Merge
Сохраняет обе линии истории. При расхождении создаёт commit с несколькими parents; при возможности может сделать fast-forward без нового commit.
Rebase
Повторно применяет commits на новой базе. Получается линейная история, но создаются новые commits с другими object IDs.
Squash merge
Берёт итоговый diff feature-ветки и создаёт один новый commit в target branch. В target не сохраняется ancestry отдельных feature commits.
Fast-forwardЕсли current branch является предком вливаемой, Git может просто передвинуть её ref вперёд. git merge --ff-only feature-x разрешает только такой случай и откажется при расхождении; --no-ff требует merge commit даже когда fast-forward возможен.
# Merge feature в current branch git switch main git merge --no-ff feature-x # Обновить свою feature-ветку линейно git switch feature-x git fetch origin git rebase origin/main

Когда что использовать:

MergeRebaseSquash
История featureсохраняетсясохраняется, но IDs меняютсясворачивается в один итоговый commit
Graphможет содержать развилкилинейныйлинейный в target
Общие branchesобычно безопасный выбортолько при явном владении и договорённостиобычно выполняет hosting platform при merge PR
Компромиссполная история, больше шумачистая история, переписываниепростой revert feature, потеря granular history в main
Правило rebaseНе переписывай protected branch и историю, на которую уже опираются другие люди, без координации. Свою опубликованную feature-ветку команды часто rebase-ят; после проверки remote tip её обновляют через git push --force-with-lease, а не голый --force.

Interactive rebase (git rebase -i origin/main) позволяет reword, squash/fixup, переупорядочить или drop собственные commits. git commit --amend переписывает только последний commit. Обе операции меняют IDs.

--force-with-lease разрешает non-fast-forward push, только если remote ref всё ещё имеет ожидаемое значение. Это защищает от случайного затирания неизвестных commits, но не превращает переписывание общей branch в хорошую идею.

Командное решениеИстория — интерфейс для расследований и откатов. Команда заранее выбирает merge policy: merge commits для сохранения контекста, rebase merge для линейности или squash merge для «один PR — один commit». Последовательная политика полезнее личного предпочтения.
Каверзный вопрос«Merge всегда создаёт merge commit?» — Нет. Если current branch является предком другой, по умолчанию возможен fast-forward: двигается только ref. Merge commit гарантирует --no-ff; --ff-only, наоборот, запрещает merge commit и падает при diverged history.
04 Конфликты слияния conflicts

Conflict означает, что Git не может автоматически построить результат трёхстороннего merge из общего предка (merge base) и двух версий. Это не только правка одной строки: одна branch могла удалить файл, который другая переименовала, обе могли добавить файл с одним именем, а binary-файл нельзя объединить построчно.

<<<<<<< HEAD current side ======= other side >>>>>>> feature-x

Как разрешить конфликт по шагам:

git merge feature-x # возник конфликт git status # unmerged paths и подсказка операции git diff --name-only --diff-filter=U # понять намерение обеих сторон, отредактировать и протестировать git add file.py # отметить path как resolved git merge --continue # либо git commit # для rebase/cherry-pick: соответствующая команда --continue
  • Current/incoming не означают «моё/чужое» во всех операциях. Во время rebase смысл ours/theirs для пользователя выглядит перевёрнутым, потому что commits переигрываются на новую базу
  • Accept both — не решение по умолчанию: можно получить дублированный код, два импорта или несовместимую бизнес-логику
  • Rename/delete и binary conflicts требуют решить судьбу path или пересоздать artifact, а не просто убрать текстовые markers
  • git merge --abort, git rebase --abort, git cherry-pick --abort возвращают состояние до незавершённой операции

Как избегать конфликтов (лучше, чем уметь их разруливать):

  • Делать небольшие изменения и регулярно интегрировать свежий target branch
  • Не смешивать массовое форматирование, rename и функциональную правку в одном PR
  • Координировать изменения общих схем, lock-файлов, fixtures и больших конфигов
  • Разбивать файлы и зоны ответственности, которые постоянно становятся точкой столкновения
Повторяющиеся конфликтыМеханизм rerere (git config rerere.enabled true) запоминает ранее выбранное resolution и может применить его снова. Это полезно при длительном rebase или повторном merge, но результат всё равно просматривают и тестируют.
Каверзный вопрос«После ручного resolution Git разрешил продолжить. Значит всё правильно?» — Нет. Git знает только, что в index больше нет unmerged entries. Он не понимает бизнес-смысл результата. Проверяю diff, собираю проект и запускаю релевантные тесты до continue/commit.
05 Командные workflows workflows

Branching workflow — договорённость о том, откуда создаются branches, как изменения проверяются и объединяются, где фиксируются releases и кто может переписывать refs. Название не заменяет конкретных правил команды.

Git Flow
main, develop, feature/release/hotfix branches. Удобен при плановых версиях и параллельной поддержке, но интеграция сложнее.
GitHub Flow
Deployable main, короткая branch, PR, review и merge. Частота deployment определяется процессом доставки, а не самим Git workflow.
Trunk-based
Частая интеграция маленьких изменений в trunk напрямую или через очень короткие branches. Незавершённое поведение отделяют от release.
WorkflowСильная сторонаЦена и риск
Git Flowявно моделирует release и hotfix; можно поддерживать несколько линийдолгоживущие branches расходятся, больше merges и backport
GitHub Flowпростой PR-процесс и понятный deployable mainнужны надёжные проверки и дисциплина маленьких PR
Trunk-basedминимальный integration delay и небольшой batch sizeтребует быстрой обратной связи и способов скрыть незавершённое поведение

Практичный PR workflow: создать branch от актуального target, делать небольшие осмысленные commits, регулярно обновляться, открыть PR, пройти review и обязательные проверки, выбрать согласованный merge method, затем удалить merged branch. Детали gates и merge queue находятся в CI/CD; здесь важна история commits и refs.

  • Protected branch запрещает прямой/force push и требует установленный процесс merge
  • Atomic commit решает одну связанную задачу и оставляет repository в рабочем состоянии; его проще review, cherry-pick, revert и bisect
  • Маленький PR уменьшает время review и риск конфликтов; механический rename/format лучше отделять от изменения поведения
  • Release branch полезна, когда версия стабилизируется отдельно или поддерживается несколько версий; иначе она добавляет backport и расхождение
Hooks и policyClient-side hooks, включая pre-commit, помогают запускать format/lint до commit, но сами hooks не передаются clone-ом и пользователь может их обойти. Обязательные правила закрепляют server-side protection и required checks, а hook-конфигурацию хранят в repository.
Каверзный вопрос«Зачем feature flags, если есть branches?» — Branch изолирует исходный код до merge; feature flag управляет release уже интегрированного и развернутого поведения. Флаг уменьшает срок жизни branch, но добавляет две ветки поведения, конфигурацию и обязанность удалить устаревший flag.
06 Отмена, восстановление, поиск recovery

Сначала определяют, что именно нужно отменить: unstaged-файл, содержимое index, local commit, уже опубликованный commit или untracked-файл. Команды с похожими названиями меняют разные области.

КомандаЧто меняетРиск
restore file.pyworking tree ← indexудаляет unstaged-правки файла
restore --staged file.pyindex ← HEADunstage без удаления working-tree правок
reset [mode] <commit>двигает current branch/HEAD; по mode меняет index и working treeпереписывает local history; --hard удаляет правки
revert <commit>создаёт новый обратный commitподходит для shared history, но возможен conflict
clean -fdудаляет untracked files/directoriesсначала preview через git clean -nd

Reset modes:

  • --soft — двигает branch/HEAD, оставляет index и working tree
  • --mixed (default) — двигает branch/HEAD и сбрасывает index, оставляет working tree
  • --hard — приводит branch, index и tracked working-tree files к указанному commit; незакоммиченные правки могут быть невосстановимы
Главная границаReflog помогает найти ранее существовавший commit, но не обязан спасать содержимое, которое никогда не было commit или stash. Перед destructive-командой проверяют status, делают backup branch/stash и используют dry-run, если он есть.

Stash временно сохраняет незавершённое состояние:

git stash push -u -m "wip login debug" # -u включает untracked git stash list git stash show -p stash@{0} git stash apply stash@{0} # применить, запись оставить git stash pop # применить и удалить при успехе

Без -u untracked-файлы обычно не входят в stash. При conflict не считают состояние потерянным: проверяют stash list, разрешают conflict и удаляют запись осознанно.

Cherry-pick применяет изменение выбранного commit поверх current branch и создаёт новый commit с новым ID. Это удобно для backport/hotfix, но массовый cherry-pick между branches создаёт расходящуюся историю и будущие конфликты.

Revert merge commit требует выбрать mainline parent: git revert -m 1 <merge-sha>. Опция говорит, какую сторону считать основной; её нельзя выбирать наугад.

Reflog и восстановлениеReflog локально записывает обновления HEAD и других refs после rebase, reset и перемещения branches. Ищут прежний SHA через git reflog и сначала создают безопасную ссылку: git switch -c rescue <sha>. Reflog не синхронизируется с remote и его записи со временем expire, поэтому это страховка, а не backup.

Как найти commit, внёсший регрессию:

git bisect start git bisect bad HEAD git bisect good v2.3.0 git bisect run pytest tests/test_login.py # 0 = good, 1..127 кроме 125 = bad, 125 = skip git bisect reset

bisect делает binary search между известными good и bad revisions. Автоматический тест должен быть детерминированным и корректно возвращать exit code; иначе найденный «виновник» ненадёжен.

ЗадачаКоманда
Увидеть graphgit log --graph --oneline --decorate --all
Найти commit по строкеgit log -S "needle" -- path
Найти commits, меняющие regexgit log -G "pattern" -- path
История конкретных строкgit blame -L 20,40 file.py, затем git show; автор строки не обязательно автор дефекта
Изменения feature от общей базыgit diff main...feature
Две и три точкиДля git diff A..B две точки фактически сравнивают endpoints A и B. git diff A...B сравнивает merge base с B — обычно это «что принесла branch B». У git log range notation имеет другую семантику, поэтому правило нельзя переносить механически.
SubmodulesSuperproject хранит не содержимое другого repository, а ссылку на точный commit. После clone зависимости получают через git submodule update --init --recursive или clone с --recurse-submodules. Пустой каталог часто означает, что submodule не инициализирован; обновление submodule требует также commit нового указателя в superproject.
Каверзный вопрос«В repository уже попал secret. Достаточно удалить файл?» — Нет: значение остаётся в старых commits и clones. Сначала немедленно revoke/rotate secret, затем при необходимости переписывают историю согласованным инструментом вроде git filter-repo, обновляют remote и координируют очистку clones. Переписывание истории не заменяет ротацию.

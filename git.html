— Формат раздела

Раздел состоит из глав с теорией и практических задач. В каждой главе разобраны команды, их назначение и вывод, который вы увидите в терминале. Задачи выполняются в виртуальном репозитории: git работает прямо в браузере, ничего не отправляется наружу.

Каждая задача запускается на свежей копии репозитория. Проверяется результат, а не текст команды: сравниваются история и ветки, содержимое рабочего каталога и индекса, состояние origin и вывод на экран. Решение, отличающееся от эталонного, засчитывается, если приводит к тому же состоянию.

Репозиторий задачКаталог ~/shop-tests — репозиторий автотестов: README.md, conftest.py, config.py, тесты в tests/ и .env с токеном. В истории три коммита, ветка main связана с origin/main. Файлы меняют так же, как в разделе Linux: printf 'текст\n' > файл перезаписывает файл, sed -i 's/старое/новое/' файл правит строку.
Отличия от настоящего gitИдентификаторы коммитов условные: они устойчивы к повторному запуску, но не равны хешам настоящего git. git log --graph рисует упрощённую схему. Интерактивные операции — редактор сообщения, rebase -i, add -p — и работа по сети не поддержаны: origin живёт внутри страницы. Остальные команды выводят то же, что настоящий git: вывод сверен с ним построчно.
  • Ctrl + Enter — выполнить команды из редактора и проверить задачу. Можно писать несколько команд, каждую с новой строки
  • Tab дополняет команды, подкоманды, пути и имена веток
  • В песочнице Enter выполняет команду, ↑ / ↓ листают историю, Ctrl + L очищает экран
  • Код и прогресс сохраняются в этом браузере

01 Репозиторий: init, status, add, commit

Git хранит историю проекта в каталоге .git рядом с файлами. Изменение проходит три области: рабочий каталог, индекс и репозиторий.

рабочий каталог --git add--> индекс --git commit--> репозиторий
  • Рабочий каталог — файлы, которые лежат на диске прямо сейчас
  • Индекс (staging area) — набор изменений, подготовленных к следующему коммиту
  • Репозиторий — сохранённые коммиты и ссылки на них внутри .git
git init · создать репозиторий

git init создаёт .git в текущем каталоге. Файлы при этом не меняются: они просто становятся видны git как неотслеживаемые.

$ git init Initialized empty Git repository in /home/qa/shop-tests/.git/
git status · что git видит сейчас

Команда показывает три группы: что подготовлено к коммиту, что изменено, но не подготовлено, и что git не отслеживает.

$ git status On branch main No commits yet Untracked files: (use "git add <file>..." to include in what will be committed) .env README.md config.py conftest.py tests/ nothing added to commit but untracked files present (use "git add" to track)

git status --short печатает то же самое двумя колонками: первая — состояние в индексе, вторая — в рабочем каталоге. ?? означает неотслеживаемый файл. В списке видно и .env с токеном: git предложит закоммитить и его, пока в репозитории нет правил исключения.

git add · положить в индекс

Аргументом может быть файл, каталог или . — всё дерево от текущего каталога. Добавление каталога берёт все файлы внутри него.

$ git add conftest.py $ git status --short A conftest.py ?? .env ?? README.md ?? config.py ?? tests/

A в первой колонке — файл добавлен в индекс. Пока он только там: коммита ещё нет.

git commit · зафиксировать снимок

Коммит сохраняет то, что лежит в индексе, а не то, что в рабочем каталоге. Сообщение задаётся флагом -m.

$ git commit -m "add fixtures" [main (root-commit) 8f2d4c1] add fixtures 1 file changed, 6 insertions(+) create mode 100644 conftest.py

В скобках — ветка и сокращённый идентификатор коммита. root-commit значит, что это первый коммит в репозитории.

git log · посмотреть историю
$ git log --oneline 8f2d4c1 (HEAD -> main) add fixtures

--oneline сжимает каждый коммит до строки. HEAD -> main показывает, где вы находитесь: HEAD указывает на ветку main, а она — на этот коммит.

Что попадает в коммитРовно содержимое индекса на момент команды. Если файл изменён после git add, в коммит уйдёт версия, которая была добавлена, а новая правка останется незастейдженной. Это видно в git status --short как MM: изменён и в индексе, и поверх него.
02 Изменения: diff, restore, .gitignore

Одно и то же изменение существует в трёх версиях: в последнем коммите, в индексе и в рабочем каталоге. Команды diff сравнивают пары из этих трёх.

КомандаЧто с чем сравнивает
git diffрабочий каталог ↔ индекс: что ещё не подготовлено
git diff --stagedиндекс ↔ последний коммит: что уйдёт в коммит
git diff HEADрабочий каталог ↔ последний коммит: все правки целиком
git diff · читать патч
$ git diff diff --git a/config.py b/config.py index 4a1f7e2..b30c95d 100644 --- a/config.py +++ b/config.py @@ -1,3 +1,3 @@ BASE_URL = "https://staging.shop.test" -TIMEOUT = 30 +TIMEOUT = 45 RETRIES = 2

- — строка из старой версии, + — из новой, пробел в начале — контекст без изменений. @@ -1,3 +1,3 @@ — номера строк: три строки начиная с первой в обеих версиях.

git restore · вернуть как было

Восстанавливает файл из индекса. Незастейдженная правка при этом теряется без предупреждения.

$ git restore config.py $ git status --short

git restore --staged файл работает на уровень выше: убирает файл из индекса, но оставляет правку в рабочем каталоге. Это отмена git add, а не отмена изменений.

.gitignore · что git не должен видеть

Файл со списком шаблонов. Git перестаёт предлагать такие файлы к добавлению, но только если они ещё не отслеживаются.

$ cat .gitignore .env __pycache__/ *.log

Уже отслеживаемый файл правило не исключит: его сначала убирают из индекса командой git rm --cached файл, оставляя на диске. Сам .gitignore коммитят — он часть договорённостей команды.

Секреты в историиЕсли файл с токеном попал в коммит, удаление файла следующим коммитом не убирает значение из истории: оно остаётся в старых коммитах и во всех клонах. Токен отзывают и выпускают заново, а историю чистят отдельно — см. справочник.
03 История: log, show, ссылки на коммиты

Коммит адресуют идентификатором, именем ветки или относительной ссылкой от них.

СсылкаКуда указывает
HEADтекущая позиция: обычно последний коммит текущей ветки
HEAD~1, HEAD~2на один и на два коммита назад по первому родителю
main, origin/mainпоследний коммит этой ветки
8f2d4c1конкретный коммит по началу идентификатора
git log · история в разных видах
$ git log --oneline -n 2 3a2487b (HEAD -> main, origin/main) add cart test and config 0fb39c5 add login test

Полный git log печатает идентификатор, автора, дату и сообщение. -n ограничивает число коммитов, --all показывает историю всех веток, а не только текущей.

git show · что именно изменил коммит
$ git show HEAD~1 commit 0fb39c5cc4c7c0b1c50c3f0e4f1a3d2c7b8e9a01 Author: QA Engineer <qa@shop.test> Date: Mon Mar 16 10:00:00 2026 +0000 add login test diff --git a/tests/test_login.py b/tests/test_login.py new file mode 100644 index 0000000..7c1e2a4 --- /dev/null +++ b/tests/test_login.py @@ -0,0 +1,2 @@ +def test_login_ok(api): + assert api.login("qa", "secret").status_code == 200

new file mode и /dev/null в левой части означают, что файл создан этим коммитом.

Сообщение коммитаПервая строка — краткая суть в повелительном наклонении: «add retry to login test», а не «исправления». По такому сообщению потом ищут причину регрессии в git log, не открывая патч.
04 Ветки: branch, switch

Ветка — это подвижная ссылка на коммит, а не копия файлов. Создание ветки почти ничего не стоит: git записывает имя и идентификатор коммита.

git switch -c · создать и перейти
$ git switch -c feature-timeout Switched to a new branch 'feature-timeout' $ git branch * feature-timeout main

Звёздочка отмечает текущую ветку. Новая ветка начинается с того же коммита, на котором вы стояли: пока в ней нет коммитов, она неотличима от main.

Коммит двигает только текущую ветку
$ git commit -am "raise timeout to 45" [feature-timeout 9c4b2e1] raise timeout to 45 1 file changed, 1 insertion(+), 1 deletion(-) $ git log --oneline -n 2 9c4b2e1 (HEAD -> feature-timeout) raise timeout to 45 3a2487b (main, origin/main) add cart test and config

-am коммитит все изменения отслеживаемых файлов без отдельного git add. Новые файлы так не попадут: git о них ещё не знает.

git switch · переключиться обратно

При переключении git приводит рабочий каталог к состоянию целевой ветки. Незакоммиченные правки он попытается сохранить, а если они мешают — откажется переключаться.

$ git switch main Switched to branch 'main' $ cat config.py BASE_URL = "https://staging.shop.test" TIMEOUT = 30 RETRIES = 2
Удаление веток

git branch -d имя удаляет ветку и отказывается это делать, если её коммиты ещё никуда не влиты. -D удаляет в любом случае.

$ git branch -d feature-timeout error: The branch 'feature-timeout' is not fully merged. If you are sure you want to delete it, run 'git branch -D feature-timeout'.
Отделённый HEADgit switch --detach 3a2487b ставит HEAD прямо на коммит, минуя ветку. Файлы переключатся на эту версию — удобно посмотреть старое состояние. Коммиты, сделанные в таком состоянии, ни к какой ветке не привязаны: чтобы не потерять их, создают ветку git switch -c имя.
05 Слияние: merge и fast-forward

git merge ветка вливает указанную ветку в текущую. Результат зависит от того, разошлись ли ветки.

Fast-forward · ветка просто сдвигается

Если в main не было новых коммитов с момента ответвления, git переставляет ссылку main вперёд. Нового коммита не появляется.

$ git merge feature-timeout Updating 3a2487b..9c4b2e1 Fast-forward config.py | 2 +- 1 file changed, 1 insertion(+), 1 deletion(-)
Коммит слияния · когда истории разошлись

Если коммиты появились в обеих ветках, git строит результат из общего предка и двух вершин и сохраняет его новым коммитом с двумя родителями.

$ git merge feature-retries Merge made by the 'ort' strategy. config.py | 2 +- 1 file changed, 1 insertion(+), 1 deletion(-)
Управление формой истории
ФлагЧто делает
--no-ffвсегда создавать коммит слияния, даже когда возможна перемотка: в истории остаётся след, что была ветка
--ff-onlyразрешить только перемотку; если истории разошлись, команда откажется работать
--abortвернуть состояние до начала слияния
Что значит «влито»Ветка считается влитой, если её последний коммит достижим из текущей. После fast-forward ветку можно удалять: её коммиты уже в main. Именно это проверяет git branch -d.
06 Конфликты слияния

Конфликт возникает, когда обе ветки изменили один и тот же участок файла относительно общего предка. Разные участки одного файла git объединяет сам.

Как выглядит конфликт
$ git merge feature-retries Auto-merging config.py CONFLICT (content): Merge conflict in config.py Automatic merge failed; fix conflicts and then commit the result.

Слияние не завершено: git оставил рабочий каталог в промежуточном состоянии и ждёт решения.

git status · что именно не сошлось
$ git status --short UU config.py $ git diff --name-only --diff-filter=U config.py

UU — файл изменён с обеих сторон и не разрешён. Полный git status печатает блок Unmerged paths и подсказывает две команды: пометить разрешение через git add или отменить слияние через git merge --abort.

Маркеры в файле
BASE_URL = "https://staging.shop.test" TIMEOUT = 30 <<<<<<< HEAD RETRIES = 3 ======= RETRIES = 5 >>>>>>> feature-retries

Между <<<<<<< и ======= — версия текущей ветки, ниже до >>>>>>> — версия вливаемой. Разрешить конфликт значит оставить в файле нужный текст и убрать все три строки-маркера.

Завершить или отменить
$ git add config.py $ git commit --no-edit [main 5e7a0d3] Merge branch 'feature-retries'

git add помечает файл разрешённым, git commit завершает слияние: с --no-edit git берёт своё сообщение вида Merge branch '…'. Если решение пока непонятно, git merge --abort возвращает репозиторий к состоянию до слияния.

Git проверяет только маркерыПосле git add git считает конфликт разрешённым, потому что в индексе больше нет неразрешённых путей. Он не знает, осмысленный ли получился код: «оставить обе стороны» легко даёт дубль импорта или две несовместимые константы. Результат смотрят глазами и прогоняют тесты.
07 Отмена: amend, reset, revert, reflog

Сначала определяют, что именно отменяют: правку файла, содержимое индекса, последний коммит или коммит, который уже видят другие. Команды с похожими именами работают в разных областях.

КомандаЧто делаетКогда подходит
git commit --amendзаменяет последний коммит новымпока коммит не опубликован
git reset --soft HEAD~1убирает коммит, правки остаются в индексепересобрать коммит иначе
git reset --mixed HEAD~1убирает коммит и очищает индекс, файлы не трогаетвернуться к правкам и пересобрать
git reset --hard HEAD~1убирает коммит вместе с правкамикогда работа точно не нужна
git revert <коммит>добавляет новый коммит с обратными изменениямиистория уже у других
git commit --amend · переписать последний коммит

Заменяет сообщение и может добавить забытые файлы из индекса. Старый коммит исчезает из ветки, у нового другой идентификатор.

$ git add tests/test_search.py $ git commit --amend -m "add search tests" [main 41c8b90] add search tests 2 files changed, 7 insertions(+) create mode 100644 tests/test_search.py
git reset · сдвинуть ветку назад

Reset переставляет текущую ветку на другой коммит. Режим решает судьбу индекса и файлов.

$ git reset --soft HEAD~1 $ git status --short M config.py

Коммита больше нет, а его содержимое лежит в индексе: M в первой колонке. После --mixed тот же файл был бы помечен M во второй колонке, после --hard правка исчезла бы совсем.

git revert · отмена без переписывания

Создаёт новый коммит, который возвращает изменения указанного. История остаётся прежней, поэтому это безопасный способ для веток, с которыми работают другие.

$ git revert --no-edit HEAD [main 7d1e4a6] Revert "raise timeout to 45" 1 file changed, 1 insertion(+), 1 deletion(-)
git reflog · куда указывал HEAD раньше

Reflog хранит локальную историю перемещений HEAD: коммиты, переключения веток, reset и rebase. По нему находят коммит, который после reset пропал из истории ветки.

$ git reflog -n 3 3a2487b HEAD@{0}: reset: moving to HEAD~1 9c4b2e1 HEAD@{1}: commit: raise timeout to 45 3a2487b HEAD@{2}: checkout: moving from feature-timeout to main

Без -n выводится весь журнал, до самого первого коммита. Запись HEAD@{1} — это ссылка: git reset --hard HEAD@{1} вернёт ветку туда, где она была до reset.

Граница восстановленияReflog помнит коммиты, но не хранит то, что коммитом никогда не было. git reset --hard и git restore уничтожают незакоммиченные правки безвозвратно. Перед такими командами состояние сохраняют коммитом в черновую ветку или через stash.
08 Rebase: линейная история

git rebase main переносит коммиты текущей ветки так, будто они были сделаны от свежего main. Коммиты не переезжают, а создаются заново: содержимое то же, идентификаторы другие.

до: A---B---C main \ D---E feature после: A---B---C main \ D'---E' feature
git rebase · перенести ветку на свежую базу
$ git switch feature-timeout $ git rebase main Successfully rebased and updated refs/heads/feature-timeout. $ git log --oneline -n 3 b81f0a2 (HEAD -> feature-timeout) raise timeout to 45 6d0c3e7 (main) add search test 3a2487b (origin/main) add cart test and config

После rebase ветка выглядит как продолжение main: слияние в main станет перемоткой, и развилки в истории не останется.

Конфликт при переносе

Git применяет коммиты по одному и останавливается на том, который не ложится на новую базу.

CONFLICT (content): Merge conflict in config.py error: could not apply 9c4b2e1... raise timeout to 45

Дальше три варианта: разрешить файл и продолжить git add + git rebase --continue; пропустить коммит git rebase --skip; вернуть всё как было git rebase --abort.

Merge или rebase
mergerebase
Историясохраняет развилку и момент слияниялинейная, развилки не видно
Идентификаторыпрежниеновые: коммиты пересозданы
Чужие веткибезопасноломает работу тем, кто уже скачал ветку
ПравилоRebase переписывает историю. Свою неопубликованную ветку переносить безопасно; общую ветку вроде main — нет: у остальных останется старая версия тех же коммитов, и следующий merge размножит их копии.
09 Stash: отложить незавершённое

Stash убирает незакоммиченные правки в отдельное хранилище и возвращает рабочий каталог к состоянию последнего коммита. Это нужно, когда надо срочно переключиться, а текущая работа не готова к коммиту.

git stash push · отложить
$ git stash push -u -m "wip retry logic" Saved working directory and index state On main: wip retry logic $ git status --short

Флаг -u добавляет в stash и неотслеживаемые файлы: без него новые файлы останутся в рабочем каталоге.

git stash list и pop · вернуть
$ git stash list stash@{0}: On main: wip retry logic $ git stash pop On branch main Your branch is up to date with 'origin/main'. Changes not staged for commit: (use "git add <file>..." to update what will be committed) (use "git restore <file>..." to discard changes in working directory) modified: config.py no changes added to commit (use "git add" and/or "git commit -a") Dropped refs/stash@{0} (2f9c1b7)

pop применяет запись и удаляет её из списка, apply применяет и оставляет. Когда записей несколько, их адресуют как stash@{1}.

Stash — не бэкапЗаписи лежат только локально, не уезжают в origin и легко теряются при чистке репозитория. Для работы дольше одного дня надёжнее черновой коммит в отдельной ветке: его видно в истории и можно отправить на сервер.
10 Удалённый репозиторий: fetch, pull, push

origin — обычное имя удалённого репозитория, а не специальное слово git. Рядом с локальными ветками существуют ссылки вида origin/main: это локальная копия того, что было на сервере в момент последнего обмена.

ИмяЧто это
mainлокальная ветка: двигается вашими коммитами
origin/mainсостояние ветки на сервере по последнему fetch
upstreamсвязь локальной ветки с веткой на сервере: по ней считается «впереди/позади»
git fetch · узнать, что на сервере

Скачивает новые коммиты и двигает origin/main. Текущая ветка и файлы не меняются: это безопасная команда.

$ git fetch origin From git@git.shop.test:qa/shop-tests 3a2487b..7f1c9d4 main -> origin/main $ git status On branch main Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded. (use "git pull" to update your local branch) nothing to commit, working tree clean
git pull · скачать и влить

git pull = fetch + интеграция. По умолчанию это слияние, с флагом --rebase — перенос ваших коммитов поверх серверных, без коммита слияния.

$ git pull --rebase From git@git.shop.test:qa/shop-tests 3a2487b..7f1c9d4 main -> origin/main Successfully rebased and updated refs/heads/main.

Первые две строки — это шаг fetch внутри pull. Если локальных коммитов нет, интегрировать нечего: обе формы команды просто перематывают ветку и печатают Fast-forward.

git push · отправить свои коммиты
$ git push -u origin feature-timeout branch 'feature-timeout' set up to track 'origin/feature-timeout'. To git@git.shop.test:qa/shop-tests.git * [new branch] feature-timeout -> feature-timeout

-u задаёт upstream: дальше в этой ветке хватает git push и git pull без имён. Если на сервере появились коммиты, которых нет у вас, push будет отклонён — сначала fetch и интеграция.

Отправка переписанной ветки

После rebase локальные коммиты заменены новыми, и обычный push отклоняется. --force-with-lease перезаписывает ветку на сервере, но только если она там осталась такой, какой вы её видели при последнем fetch.

$ git push --force-with-lease origin feature-timeout

Голый --force такой проверки не делает и затирает чужие коммиты, появившиеся после вашего fetch.

Fetch против pullFetch только обновляет представление о сервере: после него можно посмотреть git log main..origin/main и решить, сливать или переносить. Pull делает оба шага сразу, поэтому на общих ветках его поведение задают заранее: политика команды — merge или rebase.

11 Командные процессы workflows

Branching workflow — договорённость о том, откуда создаются ветки, как изменения проверяются и объединяются, где фиксируются релизы и кто может переписывать ссылки. Название не заменяет конкретных правил команды.

Git Flow
main, develop, ветки feature / release / hotfix. Удобен при плановых версиях и параллельной поддержке, но интеграция сложнее.
GitHub Flow
Деплоимый main, короткая ветка, PR, ревью и merge. Частота поставки определяется процессом доставки, а не самим workflow.
Trunk-based
Частая интеграция маленьких изменений в trunk напрямую или через очень короткие ветки. Незавершённое поведение прячут за флагами.
WorkflowСильная сторонаЦена и риск
Git Flowявно моделирует релиз и hotfix, можно вести несколько линийдолгоживущие ветки расходятся, больше слияний и backport
GitHub Flowпростой PR-процесс и понятный деплоимый mainнужны надёжные проверки и дисциплина маленьких PR
Trunk-basedминимальная задержка интеграции и небольшой объём изменений за разтребует быстрой обратной связи и способов скрыть незавершённое

Практичный PR-процесс: создать ветку от актуального target, делать небольшие осмысленные коммиты, регулярно обновляться, открыть PR, пройти ревью и обязательные проверки, выбрать согласованный способ слияния, затем удалить влитую ветку. Детали гейтов и merge queue — в CI/CD; здесь важны история коммитов и ссылки.

  • Защищённая ветка запрещает прямой и force push и требует установленный процесс слияния
  • Атомарный коммит решает одну связанную задачу и оставляет репозиторий в рабочем состоянии: его проще ревьюить, переносить, откатывать и искать через bisect
  • Маленький PR уменьшает время ревью и риск конфликтов; механический rename или форматирование лучше отделять от изменения поведения
  • Release branch полезна, когда версия стабилизируется отдельно или поддерживается несколько версий; иначе она добавляет backport и расхождение
Hooks и правилаКлиентские хуки, включая pre-commit, запускают формат и линтер до коммита, но сами хуки не передаются при клонировании, и пользователь может их обойти. Обязательные правила закрепляют на сервере: защита веток и required checks, а конфигурацию хуков хранят в репозитории.
Каверзный вопрос«Зачем feature flags, если есть ветки?» — Ветка изолирует исходный код до слияния, флаг управляет поведением уже интегрированного и развёрнутого кода. Флаг сокращает срок жизни ветки, но добавляет две ветви поведения, конфигурацию и обязанность удалить флаг потом.
12 Переписывание истории и поиск reference

Интерактивный rebase git rebase -i origin/main открывает список коммитов, в котором каждый помечают действием: reword — поменять сообщение, squash и fixup — склеить с предыдущим, drop — выбросить, строки можно переставить. Все затронутые коммиты пересоздаются с новыми идентификаторами.

Squash merge берёт итоговый diff ветки и кладёт в target одним коммитом: в основной ветке не остаётся истории отдельных коммитов ветки. Обычно это делает платформа при слиянии PR.

git rebase -i origin/main # переупорядочить, склеить, переименовать git cherry-pick <sha> # перенести один коммит в текущую ветку git revert -m 1 <merge-sha> # откат коммита слияния: 1 — основная сторона git push --force-with-lease # отправить переписанную ветку

Cherry-pick применяет изменение выбранного коммита поверх текущей ветки и создаёт новый коммит с новым идентификатором. Это удобно для backport и hotfix, но массовый перенос между ветками рождает расходящиеся истории и будущие конфликты.

Откат коммита слияния требует указать, какую сторону считать основной: -m 1. Выбор нельзя делать наугад — от него зависит, какие изменения окажутся отменёнными.

Поиск по истории

ЗадачаКоманда
Увидеть граф всех ветокgit log --graph --oneline --decorate --all
Найти коммит по строке кодаgit log -S "needle" -- path
Найти коммиты, меняющие шаблонgit log -G "pattern" -- path
История конкретных строкgit blame -L 20,40 file.py, затем git show
Что принесла ветка относительно базыgit diff main...feature

Бинарный поиск регрессии. bisect делит историю пополам между известными «хорошим» и «плохим» коммитами:

git bisect start git bisect bad HEAD git bisect good v2.3.0 git bisect run pytest tests/test_login.py # 0 — good, 1..127 кроме 125 — bad git bisect reset

Автоматический тест должен быть детерминированным и возвращать корректный код выхода, иначе найденный «виновник» ненадёжен. Автор строки в blame — тоже не обязательно автор дефекта: строку мог задеть рефакторинг или форматирование.

Две и три точкиУ git diff запись A..B сравнивает конечные состояния A и B, а A...B — общую базу с B, то есть «что принесла ветка B». У git log семантика диапазонов другая, поэтому правило нельзя переносить механически.
13 Тэги, worktree, submodules, секреты reference

Тэги фиксируют версии. Lightweight-тэг — просто ссылка. Annotated-тэг хранит автора, дату, сообщение и может быть подписан, поэтому подходит для релиза:

git tag -a v2.4.0 -m "release 2.4.0" git push origin v2.4.0 # тэги отправляются отдельно от коммитов git show v2.4.0

Опубликованный тэг не передвигают молча: имя версии должно продолжать указывать на тот же объект. Исправление выпускают новым тэгом.

Несколько задач одновременноgit worktree add ../hotfix -b hotfix origin/main создаёт второй рабочий каталог того же репозитория. Можно держать feature и hotfix в разных папках без stash и постоянных переключений; одну ветку обычно нельзя открыть в двух worktree сразу.

Submodules. Родительский репозиторий хранит не содержимое другого репозитория, а ссылку на конкретный коммит. После клонирования зависимости получают через git submodule update --init --recursive или клонируют с --recurse-submodules. Пустой каталог обычно означает неинициализированный submodule; обновление зависимости требует ещё и коммита новой ссылки в родительском репозитории.

Повторяющиеся конфликты. Механизм rerere (git config rerere.enabled true) запоминает выбранное разрешение и применяет его снова при повторном слиянии или длинном rebase. Результат всё равно просматривают и прогоняют тестами.

Секрет попал в репозиторийУдаление файла новым коммитом не убирает значение из истории: оно остаётся в старых коммитах, у всех, кто клонировал репозиторий, и в кэшах хостинга. Порядок действий: немедленно отозвать и перевыпустить секрет, затем при необходимости переписать историю согласованным инструментом вроде git filter-repo, обновить удалённый репозиторий и скоординировать обновление клонов. Переписывание истории не заменяет ротацию.
Каверзный вопрос«После ручного разрешения конфликта git разрешил продолжить — значит, всё правильно?» — Нет. Git знает только, что в индексе не осталось неразрешённых путей. Смысл результата он не проверяет: нужно прочитать итоговый diff, собрать проект и прогнать релевантные тесты до --continue или коммита.

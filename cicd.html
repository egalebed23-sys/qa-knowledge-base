01 CI/CD: что это basics

CI/CD — автоматизация сборки, тестирования и доставки кода. Три понятия, которые часто путают:

  • CI (Continuous Integration) — каждый коммит автоматически собирается и прогоняется через тесты. Баги ловятся сразу, а не «под релиз»
  • CD (Continuous Delivery) — код всегда готов к деплою, выкатка — по кнопке (ручное подтверждение)
  • CD (Continuous Deployment) — деплой в прод полностью автоматический, без ручного шага
АналогияCI — как автопрогон тестов при каждом сохранении файла, только для всей команды: каждый коммит сразу проверяется. Pipeline — конвейер функций, где выход одной стадии (собранный билд) идёт на вход следующей (тесты → деплой).

Зачем это нужно:

  • Каждый разработчик делает мелкие изолированные коммиты — меньше конфликтов при слиянии
  • Фокус на бизнес-логике, а не на ручном деплое (он автоматизирован)
  • Стандартизация: каждый коммит проходит одни и те же стадии (build, lint, тесты)
  • Ранний поиск дефектов — баг виден через минуты после коммита, а не через неделю

Delivery vs Deployment — разница в последнем шаге: Delivery доводит до состояния «готово к production», но выпуск подтверждает человек; Deployment выпускает автоматически после прохождения условий.

Инструменты: GitHub Actions, GitLab CI, Jenkins, CircleCI, TeamCity. Принцип у всех один — процесс хранится как код, запускается по заданным событиям и оставляет воспроизводимую историю результатов.

DORA-метрикиАктуальная модель состоит из пяти показателей. Throughput: change lead time, deployment frequency, failed deployment recovery time. Instability: change fail rate и deployment rework rate. Их смотрят вместе и в динамике для конкретного сервиса: скорость без стабильности не является успехом. Для QA связь прямая — медленные и нестабильные проверки увеличивают lead time, а слабые gates повышают долю неудачных изменений.

CI — это инженерная практика, а не название сервера. GitHub Actions, GitLab CI, Jenkins и TeamCity только исполняют процесс. Частая интеграция небольших изменений, быстрый feedback и исправление красного main важнее выбора инструмента.

CI/CD не равно DevOps. CI/CD — набор практик и автоматизации доставки. DevOps шире: совместная ответственность разработки и эксплуатации, инфраструктура, observability, incident response и постоянное улучшение процесса.

Каверзный вопрос«В чём разница Continuous Delivery и Continuous Deployment?» — В обоих случаях код автоматически проходит все стадии и готов к проду. Разница в финале: Delivery требует ручного нажатия кнопки «выкатить», Deployment выкатывает в прод автоматически, без человека. Deployment требует очень зрелого тестирования и мониторинга.
02 Pipeline и стадии pipeline

Pipeline — исполняемый граф работ от изменения кода до проверки и доставки. Это не всегда линейная цепочка: независимые работы идут параллельно, а зависимости образуют DAG.

build→ lint→ unit→ integration→ deploy
ПонятиеЧто означает
Pipeline / workflowвесь запуск по конкретному commit SHA
Stageлогическая фаза; jobs одной стадии обычно могут идти параллельно
Jobнезависимая единица работы на runner; её результат влияет на статус pipeline
Stepотдельная команда или action внутри job; общий workspace обычно живёт только в пределах job
Runner / agentмашина или среда, которая выполняет job

Названия у систем отличаются: GitHub Actions говорит workflow → jobs → steps, GitLab — pipeline → stages → jobs, Jenkins — pipeline → stages → steps. На собеседовании важнее понимать границы выполнения и передачи данных, чем помнить конкретный YAML.

На что запускается пайплайн (триггеры):

  • push — на каждый коммит в ветку
  • pull/merge request — при создании или обновлении PR/MR
  • schedule — по расписанию (ночной полный регресс)
  • manual — по кнопке, часто с параметрами и подтверждением
  • tag/release или upstream pipeline — при выпуске версии либо после сборки другого сервиса

Простой пример конфига (GitHub Actions):

name: CI on: [pull_request] permissions: contents: read concurrency: group: ci-${{ github.ref }} cancel-in-progress: true jobs: test: runs-on: ubuntu-latest timeout-minutes: 15 steps: - uses: actions/checkout@v7 - uses: actions/setup-python@v7 with: python-version: '3.12' cache: 'pip' - run: pip install -r requirements.txt - run: pytest --junitxml=junit.xml

Major tags в примере оставлены для читаемости. В защищённом pipeline action фиксируют на проверенный полный commit SHA, чтобы ссылка была неизменяемой.

Управление графом: needs задаёт зависимости между jobs, if/rules — условия запуска, а статус обязательных jobs образует gate. Без зависимости jobs могут выполняться параллельно; deploy должен ссылаться на проверки явно, а не надеяться на порядок строк в файле.

Два зелёных PR сломали mainКаждый PR мог тестироваться против старого состояния target branch и проходить отдельно, хотя их изменения несовместимы вместе. Require up-to-date branch, merged-results pipeline и merge queue/train проверяют синтетический merge commit и сериализуют безопасное слияние.
Тестовые зависимостиДля integration-тестов CI может предоставить БД или брокер как service, либо их создаёт сам test harness. На уровне pipeline важно обеспечить изоляцию, readiness/health check и гарантированную очистку. Реализация контейнерного окружения разобрана в Bash · Docker · K8s.

Оптимизация пайплайна:

  • Параллелизм и шардинг — независимые jobs и части suite исполняются одновременно
  • Матрица — один job запускается для набора версий Python, ОС или браузеров; fail-fast: false сохраняет результаты всех комбинаций
  • Кэш — повторно использует скачанные зависимости; ключ обычно зависит от lock-файла, а cache miss не должен ломать сборку
  • Concurrency — новый commit отменяет устаревший прогон того же PR и освобождает runner
  • Timeout и fail fast — ограничивают зависшие jobs и останавливают заведомо бесполезную ветку графа. Это не то же самое, что оборвать pytest после первого падения и потерять диагностическую картину

Секреты и безопасность pipeline:

  • Секреты хранятся в secret store CI, выдаются только нужной job и среде; обычная переменная окружения сама по себе секретом не становится
  • Маскирование логов не гарантирует защиту преобразованного или составного значения. Нельзя печатать заголовки, дампы окружения и тела запросов целиком
  • Токен pipeline получает минимальные permissions. Для облака лучше OIDC и короткоживущие credentials, чем постоянный access key
  • Недоверенный код из fork PR не должен получать production secrets. Отсутствие секрета в таком PR — защитный механизм, а не случайная поломка CI
  • Сторонние actions/plugins проверяют и фиксируют на неизменяемый commit SHA; отчёты, HAR, traces и screenshots проверяют на токены и персональные данные

Hosted vs self-hosted runners. Hosted runner обычно выдаёт чистую эфемерную среду, но имеет лимиты и не видит внутреннюю сеть. Self-hosted даёт нужную сеть, железо и ПО, однако требует патчей, изоляции и очистки; постоянный runner может сохранить файлы и состояние прошлого запуска. При расхождении local/CI проверяют версию runtime и браузера, архитектуру, timezone/locale, переменные, права, сеть, ресурсы и чистоту workspace.

Что измерятьНе существует универсальной цели «CI должен идти 10 минут». Смотрят отдельно queue time, длительность jobs и время от commit до обязательного зелёного результата, лучше по p50/p95. Оптимизируют критический путь; тяжёлые проверки переносят после merge или в расписание только после оценки риска, а не потому, что они неудобны.
Каверзный вопрос«Почему новая job не ускорила pipeline?» — Возможно, она всё ещё стоит на критическом пути из-за needs, ждёт свободный runner, конкурирует за CPU/БД, повторно скачивает зависимости или шардирование получилось неравномерным. Сначала измеряю queue time и длительность каждой job, затем меняю граф.
03 Автотесты и quality gates quality gates

Quality gate — формализованное условие, без которого изменение нельзя merge или продвинуть в следующую среду. Это может быть не только автотест: required status check, ревью, security policy или ручное подтверждение production deployment.

tests→ quality gate→ merge / deploy
Два типа проверокBlocking меняет статус pipeline и останавливает merge/deploy. Informational публикует результат, но разрешает движение дальше (allow_failure / continue-on-error). Для каждой проверки заранее определяют владельца, критерий успеха и действие при падении.

Где запускать проверки — решают по скорости, надёжности и риску:

КогдаЧто гоняем
На PR/MRlint, unit, component/contract и быстрые integration; проверки изменённого кода
После merge в mainрасширенный integration/E2E и сборка релизного кандидата
После deploy в test/stagingsmoke, миграции, критичные сквозные сценарии
По расписаниюдолгий regression, совместимость, периодические security/performance проверки
После deploy в prodбезопасный smoke/synthetic и контроль технических и бизнес-метрик

Типичные quality gates перед merge:

  • Обязательные тестовые jobs завершились успешно, flaky не спрятаны бесконечными retry
  • Линтер, статический анализ и проверка формата прошли
  • Coverage не ухудшился относительно принятой политики; новый критичный код покрыт осмысленными проверками
  • Нет уязвимостей запрещённой severity или нарушений license/policy
  • Получены требуемые approvals, ветка актуальна и защищена от прямого push

Smoke / sanity / regression в CI — когда что:

  • Smoke — короткий набор критичных проверок после каждого deploy: «версия поднялась и ключевой путь жив?»
  • Sanity — узкая проверка изменённой зоны или исправления
  • Regression — проверка ранее работавшего поведения; её объём и момент запуска зависят от риска и длительности, а не от самого названия

Pre-merge vs post-merge: быстрые надёжные проверки блокируют дефект до merge. Долгие проверки можно запускать после merge или по расписанию, но у красного main всё равно должны быть owner, уведомление и правило восстановления. «Не блокирует PR» не означает «можно игнорировать».

Как проектировать gateГейт должен быть воспроизводимым, достаточно быстрым для своего места, иметь низкий flaky rate и отражать реальный риск. Исключения делаются явно и аудируемо. Если проверку постоянно обходят, разбирают её ценность, стабильность и стоимость, а не привыкают к красному статусу.
Каверзный вопрос«Тесты идут 40 минут на каждый PR. Что делаешь?» — Сначала строю профиль времени и падений. Затем убираю дубли и ожидания, переношу проверки на более дешёвый уровень, шардирую сбалансированно, кэширую зависимости, чиню flaky и разделяю blocking/informational по риску. Просто вынести всё на ночь — увеличить время обнаружения дефекта.

Виды покрытия: что вообще значит «покрытие 80%»

Гейт выше говорит «coverage не упал ниже порога». На собесе спросят, какое именно покрытие имеется в виду — и это разные метрики разной строгости.

ВидЧто считаетСтрогость
Statement (строк)какие строки исполнились хоть разсамое слабое, показывается по умолчанию
Branch (ветвей)прошли ли оба исхода каждого ветвлениястроже: строка с if исполнилась, а ветка else — ни разу
Conditionкаждое подусловие внутри сложного условияещё строже
Path (путей)все комбинации путей через функциюна практике недостижимо, растёт комбинаторно

Наглядно: для if a and b: один тест с a=True, b=True даёт 100% statement и всего 50% branch — ветка «условие ложно» не исполнялась ни разу.

Цикломатическая сложность оценивает число линейно независимых путей. Рост значения означает больше вариантов для анализа и тест-дизайна, но сама метрика не сообщает, какие бизнес-риски покрыты и сколько тестов «достаточно».

Каверзный вопрос«У нас 85% покрытия. Это хорошо?» — Само по себе ни о чём не говорит. Уточню три вещи: какое покрытие — строк или ветвей; что именно в этих 85% — критичная бизнес-логика или геттеры и конфиги; есть ли в тестах утверждения. Тест без единого assert даёт покрытие, но не проверяет ничего. 60% на платёжном модуле с осмысленными проверками лучше 85% на автосгенерированных тестах.
В реальном миреУниверсального «достаточного» процента не существует. Работает дифференцированный подход: выше требования к критичной бизнес-логике, ниже — к UI-обвязке и генерируемому коду. Часто отдельно контролируют coverage нового кода и отсутствие деградации общего уровня, но процент остаётся индикатором, а не доказательством качества.
04 Стратегии деплоя deployment

Deployment доставляет новую версию в среду. Основные стратегии отличаются наличием простоя, стоимостью инфраструктуры, скоростью отката и временем, когда старая и новая версии работают одновременно.

Recreate
Старую версию останавливают, затем запускают новую. Просто и дёшево, но есть downtime; подходит не для каждого production-сервиса.
Rolling
Инстансы обновляют партиями. Простоя обычно нет, но две версии временно работают вместе и должны быть совместимы с API, данными и очередями.
Blue / Green
Новую версию разворачивают в параллельной среде, проверяют и переключают на неё трафик целиком. Откат быстр, но две среды стоят дороже, а данные остаются общим риском.
Canary
Новая версия получает малую долю трафика. Долю увеличивают поэтапно, если функциональные, технические и бизнес-метрики не ухудшаются.
Deployment ≠ releaseFeature flag управляет доступностью уже развернутой функции и отделяет release от deployment. Выключение флага может быстро убрать пользовательский эффект, но не откатывает миграцию, нагрузку, фоновую задачу или несовместимое изменение API.

Rollback возвращает предыдущую версию; roll-forward выпускает исправленную следующую. Выбор зависит от обратной совместимости данных, скорости восстановления и цены повторного deploy. План восстановления и критерии решения готовят до релиза.

Как тестировать каждую стратегию:

  • Rolling — совместимость старых и новых инстансов, long-lived sessions, очереди, кэш и поведение во время частичного обновления
  • Blue/green — smoke на новой среде до переключения, корректность маршрутизации и доступность общей БД после переключения
  • Canary — репрезентативность выбранного трафика, smoke/synthetic и автоматические пороги error rate, latency и бизнес-метрик
  • Feature flag — обе ветки, права и сегменты пользователей, значение по умолчанию, выключение без deploy и удаление устаревшего флага
  • Rollback/roll-forward — версия действительно сменилась, сервис восстановился в целевое время, данные не потеряны и читаются
Progressive deliveryCanary, feature flags и автоматический анализ метрик уменьшают радиус воздействия, но не заменяют pre-production проверки. После каждого шага нужен наблюдаемый критерий продолжить, остановить или вернуть изменение.

Основной риск — миграции БД при rollback. Код откатить легко, а схему БД — нет. Если новая версия добавила/изменила колонку, откат кода на старую версию может сломаться о новую схему.

  • Решение: backward-compatible миграции. Сначала добавить колонку (старый код её игнорирует), потом выкатить код, который её использует. Удалять старое — только через несколько релизов
  • Это называется expand-contract (или parallel change): расширяем схему → мигрируем → сужаем
Dark launchКод выполняется в production на реальном или зеркалируемом трафике, но результат ещё не показывается пользователю и не должен менять бизнес-состояние. Так проверяют производительность и сравнивают результаты до публичного release.
Каверзный вопрос«Blue/green гарантирует мгновенный rollback?» — Только для stateless-кода. Общая БД уже могла получить новую схему и данные, сообщения могли уйти во внешние системы, а кэш и сессии — измениться. Поэтому проверяют backward compatibility и репетируют восстановление целиком, а не только переключение трафика.
05 Артефакты и окружения delivery

Artifact — сохранённый результат job. Он нужен другой job, человеку для разбора или системе доставки. Cache — только ускоритель: его отсутствие не должно менять результат сборки.

ЧтоПримерыТребование
Release artifactwheel/JAR, бинарник, архив, container imageнеизменяемый, однозначно связан с commit и продвигается между средами
Test artifactJUnit XML, Allure results, screenshots, traces, coverageдоступен для диагностики, имеет retention и не содержит секретов
Cachepip/npm packages, результаты компиляцииможет устареть или отсутствовать; ключ зависит от lock-файла и платформы

Build once, promote many: release artifact собирают один раз, тестируют именно его и затем продвигают в staging и production. Пересборка «того же commit» для каждой среды создаёт разные бинарные результаты и обесценивает проверку.

build + version→ verify→ staging→ approval→ production
  • Версия содержит уникальный идентификатор: release version и/или commit SHA; тег вроде latest не даёт воспроизводимости
  • В metadata сохраняют source SHA, build ID, время, результаты проверок и зависимости; checksum/signature помогают убедиться, что artifact не подменился
  • SBOM перечисляет компоненты, provenance описывает происхождение сборки; это элементы защиты supply chain, а не замена тестам
  • Registry/artifact storage настраивают с retention, ограничением доступа и запретом перезаписи релизных версий

Environment — цель развертывания с собственными настройками, данными, интеграциями и правами: dev, test/qa, staging, production. Конфигурацию отделяют от artifact: одна версия получает разные environment-specific values и secrets без пересборки.

Environment parity не означает полную копию production. Важна эквивалентность по проверяемым рискам: версии сервисов, схема БД, конфигурация, маршрутизация и интеграционные контракты. Объём данных и нагрузка могут отличаться, поэтому зелёный staging не отменяет production monitoring.

Граница с DockerPipeline может выполнять jobs и service dependencies в контейнерах, а release artifact может быть образом. Здесь важно, как artifact версионируется, проверяется и продвигается. Dockerfile, image/container, Compose, volumes, сети, Testcontainers и Kubernetes разобраны в Bash · Docker · K8s и здесь не повторяются.
Каверзный вопрос«Чем artifact отличается от cache?» — Artifact является результатом конкретной сборки и нужен для передачи, доставки или диагностики. Cache можно удалить и восстановить: он только сокращает время. Деплоить приложение из cache — потерять однозначную связь с проверенной сборкой.
06 CI/CD в работе QA practice

QA в CI/CD отвечает не за «последнюю зелёную кнопку», а за качество обратной связи: какие риски проверяются, где стоит gate, насколько результату можно доверять и достаточно ли данных для быстрого разбора.

  • Встроить проверки в нужные триггеры и места pipeline, настроить exit codes и required checks
  • Подготовить изолированные test data, зависимости и cleanup для параллельных запусков
  • Держать suite быстрым, детерминированным и наблюдаемым
  • Публиковать machine-readable report и диагностические artifacts даже при падении job
  • Участвовать в post-deploy verification и правилах rollback/roll-forward

Как разбирать красный pipeline:

  1. Найти первую причинную ошибку, а не десятки последующих: trigger, commit SHA, failed job/step и exit code.
  2. Сравнить diff и предыдущий успешный запуск; проверить, воспроизводится ли проблема на том же artifact и окружении.
  3. Изучить JUnit report, stack trace, логи приложения, screenshot/video/trace, request ID и метрики.
  4. Классифицировать: дефект продукта, дефект теста, тестовые данные, environment/config, инфраструктура runner/network или известная flaky-проблема.
  5. Назначить owner и действие. Перезапуск допустим как диагностический эксперимент, но «перезапустить до зелёного» не является исправлением.
Локально зелёное, в CI красноеСравнивают точный commit и команды, версии runtime/dependencies/browser, OS/architecture, timezone/locale, переменные и secrets, права пользователя, сеть, ресурсы, порядок и параллельность тестов, состояние данных и readiness сервисов. Затем воспроизводят в максимально близкой среде, а не сразу добавляют retry.

Flaky test даёт разные результаты на одинаковом коде и входных условиях. Причина существует, даже если она пока не найдена: race condition, зависимость от порядка, общий state, случайность без seed, нестабильная сеть, неверное ожидание, ресурсы или время.

  • Сохраняют pass-after-retry как flaky-событие, иначе статистика врёт
  • Собирают частоту, duration, runner, seed, порядок тестов и diagnostics; воспроизводят многократным запуском и меняют порядок/нагрузку
  • Нестабильную проверку временно выводят из blocking gate только по quarantine policy: задача, owner, срок и критерий возврата
  • Retry ограничивают и используют для диагностики или известной внешней нестабильности; он не устраняет первопричину

Как ускорить suite, который идёт два часа:

  • Сначала измерить setup, collection и duration каждого теста; найти медленный хвост, повторы, ожидания и инфраструктурные паузы
  • Перенести проверки на более дешёвый уровень: часть E2E заменить component/contract/integration тестами без потери риска
  • Запускать независимые тесты через pytest-xdist, а suite делить на сбалансированные по истории времени shards
  • Изолировать аккаунты, данные и namespaces; иначе параллелизация создаст гонки и упрётся в общую БД
  • На PR выбирать релевантные тесты по изменению, сохраняя полный периодический прогон как контроль пропущенных зависимостей

Отчётность: CI обычно читает JUnit XML и показывает статус, имя теста, duration и ошибку. Allure или аналог даёт человеку шаги, историю и attachments. Для UI/API полезны screenshot, video, trace, request/response без секретов, server logs и correlation ID. Публикацию настраивают с условием always(), чтобы отчет не исчезал именно при падении.

Что проверять на review pipeline-конфига:

  • Нужные ли branches/events/paths запускают workflow, нет ли двойных запусков на push и PR
  • Верно ли построены dependencies и gates; действительно ли deploy получает проверенный artifact
  • Есть ли timeout, cleanup, отмена устаревших запусков и корректное поведение при concurrent pipelines
  • Минимальны ли token permissions и область secrets; безопасен ли запуск для fork PR и third-party actions
  • Сохраняются ли reports/artifacts при failure, ограничены ли доступ и retention
Deployment verificationПосле deploy сверяют ожидаемую версию, readiness и health, выполняют безопасный smoke/synthetic и наблюдают error rate, latency, saturation и ключевые бизнес-метрики относительно baseline. Заранее заданные пороги определяют продолжение canary, остановку, rollback или roll-forward. Deploy завершён технически не тогда, когда команда отработала без ошибки, а когда система подтвердила здоровье.
Как оценивать valueСмотрят вместе: сколько реальных регрессий найдено до production, escaped defects, flaky rate и pass-after-retry, длительность и p95 feedback, время диагностики, долю ложных тревог и случаи обхода gates. Один счётчик тестов или высокий coverage легко улучшить без улучшения качества.
Каверзный вопрос«Кто должен чинить красный pipeline?» — Владение общее и определяется причиной: разработчик исправляет регрессию продукта, автор теста — дефект проверки, platform/DevOps — runner или инфраструктуру. QA помогает быстро классифицировать и обеспечить диагностику; роль QA не в том, чтобы молча перезапускать всё красное.
